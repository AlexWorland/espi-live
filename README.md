# ESPI live viewer

A live viewer for a FLIR Blackfly (BFS-U3-63S4M-C) Mono8 camera used for ESPI (electronic speckle pattern interferometry) measurements. Python, PySpin/Spinnaker, OpenCV and Qt (PySide6), with GPU-accelerated display; runs on Windows, macOS and Linux.

The connected camera's model is detected automatically (from its GenICam identity nodes) and shown in the window title, status badge and Camera controls. Other FLIR/Teledyne models (other Blackfly S sensors, Grasshopper, Chameleon, Oryx) are named and run with the limits they report, with a note in the log when a model is untested or colour; see `docs/camera/supported-models.md`.

The analog **Sony XC-ST50** works too, through a **Hauppauge USB-Live2** capture stick, alongside a Blackfly or on its own; see [Analog camera](#analog-camera-sony-xc-st50) below.

**Help > User Guide** (also **F1**) opens the illustrated offline [user guide](src/espi_live/user_guide.html) in the default browser; its search box (press `/`) highlights matches anywhere in the guide.

## Quick start

```sh
# Any machine (no camera or PySpin needed): synthetic video
./run.sh --demo

# Camera PC (Windows, Python 3.10 with PySpin): double-click
scripts/windows/SETUP AND START ESPI.bat
```

Manually: `PYTHONPATH=src python -m espi_live [--demo]` (on Windows, `set PYTHONPATH=src` first). Run it with an interpreter that has the packages in `requirements.txt` (OpenCV, NumPy, PySide6); the camera runtime also needs PySpin, normally `C:\Python310\PySpin\python.exe`. PySide6 is required; without it the app exits with a message. `python -m espi_live --check` loads everything without opening a window; `python -m unittest discover -s tests` runs the camera-free tests (both with `PYTHONPATH=src`). `python scripts/run_tests.py` runs the same tests in parallel, one worker process per CPU core (about 3x faster), and applies the coverage gate below (`--no-coverage` skips it, `-j N` sets the worker count). For line coverage (kept at 100%), `pip install coverage`, then `QT_QPA_PLATFORM=offscreen python -m coverage run -m unittest discover -s tests` and `python -m coverage report`.

The normal suite includes updater integration tests with real Qt widgets, background workers, loopback HTTP and temporary installations. To also test native self-replacement, install `pyinstaller` and `certifi`, then run `PYTHONPATH=src QT_QPA_PLATFORM=offscreen python -m unittest discover -s tests/e2e -v`. This builds two disposable PyInstaller copies and tests startup and periodic discovery, manual checking, deferred restart and `--update`, including a healthy demo stream after restart and old-build cleanup. It uses no camera, SDK, GitHub credentials or external service; the only HTTP traffic is to a local fixture. The test-only launcher scripts supply build metadata, isolate settings and drive the real app; they are never included in release builds. Set `ESPI_TEST_ARTIFACTS` to a folder to retain process events and logs. The **Update end-to-end tests** workflow runs both the updater integration tests and the native tests on Windows for pull requests and as a release build gate. These tests cover native update mechanics, not camera-driver behavior or GitHub availability.

## Prebuilt binaries

Download the newest build from **https://github.com/AlexWorland/espi-live/releases/latest**; no GitHub account is needed. The Windows archive holds an `espi-live` folder: run `espi-live.exe` inside it, and keep the folder together, because the program loads its libraries from the `_internal-N` folder beside it (N is the build number). Nothing is unpacked at startup, unlike the single-file builds up to build 6, which extracted everything to a temporary folder on every start.

Releases are started by hand, so several merges can pile up and go out as one release. Merging into `main` only updates the **draft release** (on **Releases**), which previews the next one.

1. After every merge into `main`, `.github/workflows/release-drafter.yml` rewrites the draft release with release-drafter: the pull requests merged since the last release become the draft's notes, and their labels pick the next version tag (`vX.Y.Z`): `enhancement` raises the minor version, `major` the major version, anything else the patch version; `skip-changelog` leaves a pull request out. Label a pull request before merging it. Nothing is built or released.
2. When the merged changes are ready to ship, open **Actions > Release > Run workflow**, pick `main` and run it. It runs the test suite on Linux, builds the self-contained PyInstaller binary for Windows, and creates the release with the binary attached and GitHub's generated release notes (every pull request merged since the previous release, grouped by `.github/release.yml` with the same labels as the drafter), below anything typed into **Notes**. Installed copies are offered it at once. If a test fails or line coverage of `src/espi_live/` is below 100%, or the build fails, nothing is released; fix it and run the workflow again.
3. The release is tagged with a version: the one typed into **Version** (`vX.Y.Z`), or else the version the draft proposes, or else the next patch version after the newest release; a version whose tag already exists is skipped. After a full release the draft is refreshed to propose the next version.

Untick **Publish** to only test and build a branch ("Use workflow from"): the archives stay on the run's page as artifacts and nothing is released. When the branch is not `main` or **Pre-release** is ticked, the release is a pre-release tagged `vX.Y.Z-pre.N` (N is the build number), which installed copies are not offered and which leaves `vX.Y.Z` for the real release.

**Quick release** is the same build, smoke test and packaging without the test suite, the coverage gate and the update tests, so a build is out in minutes. It runs automatically on every merge into `main` while the project is in active development (each merge becomes the next patch version, with GitHub's generated notes; if merges land faster than builds finish, one release covers several of them), and by hand from **Actions > Quick release > Run workflow** from any branch. It publishes as **Release** does: from any branch it makes a full release tagged `vX.Y.Z` (the draft's version, else the next patch), marked latest, so **installed copies are offered it**, and it refreshes the draft afterwards. A hand-started run can tick **Pre-release** to publish a `vX.Y.Z-dev.N` pre-release instead, which installed copies are not offered, or untick **Publish** to only build. Because it skips the tests, use it for builds you want in the lab quickly and run **Release** from `main` for a tested one. The two workflows share one build-number sequence and one concurrency group (see below).

Publishing the draft by hand (**Releases** > the draft > **Edit** > **Publish release**) also works: it creates the tag on `main` and starts the same workflow, which turns the release back into a draft while it works and publishes it again with the binaries attached (tick **Set as a pre-release** for a test build that installed copies are not offered). If that build fails the release stays a draft: delete its tag (`git push origin --delete vX.Y.Z`), fix the problem and publish again.

### Automatic updates

Prebuilt copies update themselves to the newest full release (pre-releases are skipped). The Qt interface checks GitHub in the background at startup and again about every three hours (a little earlier or later, so many cameras do not ask at the same moment). A check waits while a recording or a frame save is in progress, and a failed check is only written to the log. When a newer build exists, a blue **Install update** button appears in the status bar (the versions are in its tooltip, and the log notes the build); the status bar mentions it once, and later checks that find the same build leave the button as it is. Clicking it downloads the build while measurement continues, verifies its SHA-256, then the button reads **Restart to update**: the app finishes any recording, releases the camera, swaps in the new build and starts it with the same options. Choosing not to restart installs it when you close the app. The **Check for updates** button in the status bar (the circular-arrow icon, or **Help > Check for updates…**) checks on demand and reports the result in a dialog; it is greyed out while a check runs, and the blue button takes its place once a newer build is found. **Help > About** shows the release version and build number, and the main window's title carries the version too (for example `ESPI live v0.10.0 — BFS-U3-63S4M`; a source checkout shows `dev`).

- The first start after an update shows a **What's new** window with the notes from the GitHub Releases page for every full release the update moved past (newest first, each with a link to its release page). The download and platform notes every release repeats are left out. The notes are fetched with the update check and saved beside the program, so the window needs no network and appears once, also after `espi-live --update`.
- `espi-live --update` updates without opening a window; `--version` prints the version and build; `--no-update-check` skips the startup check, the later checks, and the startup download of the source code (see [Open in Codex](#open-in-codex)).
- The program's folder must be writable: the new build is unpacked there, its `_internal-N` folder is moved in beside the running build's, and the executable is swapped, the running one being kept as `espi-live.exe.old` (Windows cannot overwrite or delete a running program or the libraries it has loaded). When the new build starts it deletes the old executable and then the old `_internal-N` folder by itself; while the old build is still closing it retries in the background for about a minute, and anything still in use then goes at the next start. `output/` and the token files are never touched, and the log lists what was removed.
- Copies that are a single file (build 6 and earlier) cannot update themselves to the folder layout: their check reports `build N has no espi-live-windows-x64.zip` (or the Linux archive). Download a current release once by hand and unpack it where the old copy is. When the new build starts, it deletes an old single-file `espi-live.exe` (`espi-live` on Linux) in the folder above its own folder or the one above that (where Windows' **Extract all** puts it), with that copy's update leftovers. It deletes only files it recognizes as single-file builds of ESPI live, and the old copy's `output/` folder (recordings, frames, logs) stays where it is.
- The version is the release's tag (`vX.Y.Z`, or `vX.Y.Z-pre.N` for a pre-release), which the Release workflow's `version` job picks and bakes into the build; it is for people to read. Builds are ordered by the build number, which the `version` job of both **Release** and **Quick release** picks: the workflow run number, or one above the newest build any published release holds when that is higher (each workflow counts its own runs, so the run number alone would let a build rank below one already installed). A copy therefore never "updates" to an older build. Running from source never updates itself; use `git pull`.
- The repository is public, so installed copies read releases without a token. The optional `UPDATE_TOKEN` repository secret (a fine-grained token with **Contents: read-only**) is baked in when set and only raises GitHub's API rate limit; `update-token.txt` beside the program or the `ESPI_UPDATE_TOKEN` environment variable overrides it.

### Feature requests

The **Request feature** button in the status bar (the light-bulb icon; also **Help > Request a feature…**) asks for a title, an optional description and an optional name, then files a GitHub issue labelled `feature-request` and `enrich` in this repository in the background. The issue includes the build, platform and video source (camera or dummy mode). **Submit** files it from the app. When it is sent, a dialog says the request was submitted; if sending fails, you can edit and retry. The description is optional: leave it blank and the request is written from the title, or write one and that text is kept and expanded.

- The `enrich` label starts `.github/workflows/enrich-feature-request.yml`, which asks GitHub Copilot (through `actions/ai-inference`) for a structured spec (summary, motivation, proposed behavior, acceptance criteria, open questions) and appends it below the original text. The label is then replaced with `enriched`. Maintainers can add `enrich` to any issue by hand to get the same result. The system prompt is `.github/prompts/enrich-feature-request.txt`.
- Builds file issues with a token from the `FEEDBACK_TOKEN` repository secret: a fine-grained personal access token limited to this repository with **Issues: read and write** only. The release build stops if that secret is empty, so a published binary always contains it (`--check` says `feedback token: present` and never prints the token). It is separate from `UPDATE_TOKEN`, so it can be revoked without breaking updates; anyone can extract it from a public binary, so the worst case is unwanted issues (and, through the `enrich` label, Copilot runs on them). `feedback-token.txt` beside the program or the `ESPI_FEEDBACK_TOKEN` environment variable overrides it. A copy without a token cannot file the request and says so.
- Enrichment needs the `COPILOT_PAT` repository secret: a fine-grained personal access token from an account with a Copilot plan, with the **Copilot Requests** permission. Without it, the workflow comments on the issue that enrichment is not configured.

### Logs and automatic error reports

The run log is `output/logs/espi_<timestamp>.log` (the newest 50 run logs and any older active runs are kept; inactive older logs and their crash files are deleted at the next start). Every line reads `HH:MM:SS LEVEL [thread] message`, and the first lines record the build and commit time, the platform, the loaded library versions (Python, NumPy, OpenCV, PySide6, PySpin/Spinnaker), the front end and the log level. `--log-level {debug,info,warning}` or the `ESPI_LOG_LEVEL` environment variable raises the detail level (`debug` adds camera node writes, settings changes and frame timing). **Help > Open log folder** opens the folder in the file manager. When the program dies in native code (a crash inside PySpin, OpenCV or the GL driver), `faulthandler` writes `espi_<timestamp>.crash`, which the next start reports, appends to that run's log and deletes (the report includes the sanitized crash stack; the previous run's log is not attached to the public report, but it reaches the private logs repository, see below); a UI stall longer than about 10 seconds dumps every thread's stack into the log while the program keeps running.

For intermittent blur or reduced detail lasting a few seconds, the log also records its likely cause: `Frame gap` (no good frame for much longer than the frame interval), `Incomplete-frame burst`, `Camera stream counters rose` (frames the camera link lost), and `Sharpness drop` / `Sharpness recovered` for both the camera frame and the displayed frame, each with the settings in force. If only the displayed frame loses sharpness, a temporal filter (noise reduction or averaging) or smoothing is responsible; if neither does, look at the `Display:` lines (`--log-level debug`) for the size the image is drawn at. Update checks, source-copy downloads and error-report sends log when they start and finish, so they can be matched to an episode.

Unexpected errors — an uncaught exception on any thread, an engine or recorder failure, a Qt critical message, or the crash file of the previous run — are saved to `output/logs/pending_reports/` and sent automatically as GitHub issues labelled `auto-error`. Each error gets a deterministic ID (`ESPI-ERR-v1-…`, computed from the exception type and the code path it crossed, printed in the issue title and body), so the same bug is reported once no matter which machine, install path or run hit it: an existing issue gets one "seen again" comment per build, an issue closed as fixed and hit again in a newer build is reopened, and wontfix issues stay quiet. Reports are public, so they are scrubbed: no home folder, user or host name, camera serial number, saved file name, e-mail address or token-like string survives, and the body carries the build, platform, library versions, the scrubbed last log lines and the traceback. Expected conditions (no camera, camera busy, network failures, a full disk) are only logged, never reported.

- Release builds report by default; source checkouts don't, unless `ESPI_ERROR_REPORTS=1` is set. `--no-error-reports`, `ESPI_ERROR_REPORTS=0` or unticking **Help > Send error reports automatically** turns reporting off, and the log says how the first time a report is sent. Copies without the feedback token offer a **Report in browser…** link instead of filing silently.
- Run logs are uploaded silently to the **private** repository `AlexWorland/espi-live-logs` (`log_uploads.py`), so a problem can be investigated from the user's history without asking them for logs. Each run's log lands at `logs/<YYYY-MM-DD>/<HHMMSS>-<machine>.log` (the run's start time; `<machine>` is a random ID kept in `output/logs/machine-id.txt`, so one PC can be followed without its host name). A pass runs at startup (earlier runs that were never sent or grew since, such as a run that crashed) and every 15 minutes (the current run, updated in place); `output/logs/log_uploads.json` records what was sent. Logs go through the same scrubbing as error reports, plus every camera serial number this PC has seen (`output/logs/known-serials.json`) and camera labels such as `Model (12345678)`, and are capped at 5 MB (the start and the newest part). The first pass waits until the cameras are open. Uploads have no switch (the error-report switches do not affect them); failures are logged at DEBUG and never shown or reported. Builds embed the `LOGS_TOKEN` secret, a fine-grained token with only **Contents: read & write** on that one repository (`ESPI_LOGS_TOKEN` or `logs-token.txt` beside the program overrides it); without it the build only warns and the copy does not upload. `--check` says whether the token is present.
- While a real camera (FLIR or a supported capture adapter, never demo, never an iPhone) is processing, the program silently uploads scheduled captures to the **private** repository `AlexWorland/espi-live-captures` (`capture_uploads.py`, `snapshots.py`): per camera a raw and a processed still every 30 minutes and a raw and a processed 5 s clip every 6 hours, as `captures/<YYYY-MM-DD>/<HHMMSS>-<machine>-<camera>-<raw|processed>.<png|avi>` plus a `.json` sidecar with the processing and camera settings (no serial numbers anywhere in names or sidecars). Captures wait in `output/captures/pending/` until uploaded (queue capped at 200 MB; `schedule.json` keeps the schedule and the daily budget: 60 MB a day per PC, 30 MB of it reserved for clips; files over 3 MB (stills) or 7 MB (clips) are downscaled). A clip is skipped while you are recording or when fewer than 2 processed frames a second are published. Uploads have no switch and failures are logged at DEBUG only. Builds embed the `CAPTURES_TOKEN` secret, a fine-grained token with only **Contents: read & write** on that one repository (`ESPI_CAPTURES_TOKEN` or `captures-token.txt` beside the program overrides it); images cannot be scrubbed, so that token can read every upload. Without it the build only warns and the copy does not upload. `--check` says whether the token is present.
- Create the `auto-error` label in the repository before enabling automatic reports. Automatic reports are added to the **ESPI Live roadmap** project by `.github/workflows/add-error-to-project.yml`, which needs the `PROJECT_PAT` repository secret (a token with **projects: write** for this repository; the app's issue token cannot reach projects).

### Open in Codex

Prebuilt copies keep the source code they were built from in `espi-live-source/` next to the program (next to the `.app` on macOS). At startup the program checks that the folder holds its own build's commit and, if not, downloads it from GitHub in the background (about 300 KB); `.espi/download.zip` inside it keeps the original download. After an update the folder is replaced with the new build's source, unless it holds changes that were never sent, which are kept.

The **Open in Codex** button in the status bar (the `</>` icon; also **Help > Ask Codex about the source code…**) opens OpenAI's Codex command-line tool (the `codex` command) in a new terminal window in that folder, so anyone curious about how ESPI live works can ask questions that are answered from the real code. It reads **Getting source…** while the source downloads first. The first time, a dialog explains what happens and links to the Codex install page. If the `codex` command is not found (on `PATH`, or in the usual Homebrew/npm folders on macOS and Linux), a dialog says so and links to the install page; Codex is opened through the terminal on Windows (`cmd`), macOS (Terminal.app) and Linux (the first of `x-terminal-emulator`, `gnome-terminal`, `konsole`, `xfce4-terminal`, `xterm`). The Codex app is not used: its `codex://` link needs the app registered on the computer, and Windows then shows its own "Get an app to open this 'codex' link" box instead of reporting failure.

- Before opening, the program writes `AGENTS.override.md` into the folder; Codex reads it instead of `AGENTS.md`. It tells Codex that the person is not a developer: answer from the code in plain words; for a change, follow `AGENTS.md`'s rules, explain the change and ask whether they are happy with it; and only after a clear yes, write `CHANGE_REQUEST.md` (title and description) and run `espi-live --send-changes`, never git.
- `--send-changes` compares the folder with the original download (text files only; caches, `output/` and the files written for Codex are left out) and files a GitHub issue labelled `codex-change` with the description, the build, the base commit, a readable diff and the exact patch (gzip and base64). It uses the same Issues-only `FEEDBACK_TOKEN` as feature requests: no credential that can write code is in the program. Sending the same changes again only prints the earlier link; later changes go out as a new issue that includes the earlier ones.
- `.github/workflows/codex-change.yml` turns such issues (filed by the owner's token, so from the owner, a member or a collaborator) into a pull request: it reads the issue with `python -m espi_live.changes extract`, applies the patch to a new `codex/issue-<n>` branch from the base commit, opens a pull request labelled `codex-change` and closes the issue with a link. Patches that touch `.github/` or reach outside the project are refused, and a patch that does not apply is reported on the issue. The workflow needs **Settings > Actions > General > Allow GitHub Actions to create and approve pull requests**.
- Prebuilt copies cannot run the tests (they have no Python), so these pull requests arrive untested; review them like any outside contribution. Running from source, **Open in Codex** opens the checkout itself with the developers' `AGENTS.md`, and changes go through git as usual.

## Using the viewer

One window holds the image, a toolbar with the **Simple UI** switch (basic controls only, or every control; remembered between runs), the view mode, Record, Freeze, Save frame, Set reference, Compare and the reset buttons, a **Controls** panel for camera, measurement and display settings, and a **Log** panel; both panels can be docked on any side, floated as separate windows, or hidden from the **View** menu, and the layout is remembered. The status bar shows a rotating **Did you know** tip, the current view's hint, FROZEN while the display is frozen, the Check for updates, Request feature and Open in Codex buttons (small icons, named in their tooltips, so the readouts keep their room), a separator, then the source (Camera or DUMMY MODE), the recording state, the measurement range, processing and display rates, and the value of the pixel under the cursor. The tip changes about every 12 seconds, starting on a random one; click it for the next. Right-click it, or uncheck **View > Help tips**, to turn the tips off, and that choice is remembered. The status bar adapts to the window width: on a wide window everything sits on one row; on a narrower one the readouts and buttons wrap onto a second (or third) row beneath the hint, so no readout is cut short and the bar only grows by the rows it needs. The view hint always keeps its whole sentence; the tip takes what is left of the first row and is shortened with an ellipsis when that is little. Each readout has a fixed width, so a changing value never moves its neighbours. The first launch opens wide enough for the whole tip where the screen allows; the window always fits the screen it is on, and the Controls panel scrolls when the screen is too short for it.

Camera acquisition and ESPI processing run on their own thread, so moving, resizing or interacting with the window never pauses a measurement or a recording. The image is drawn by the GPU (OpenGL 3.3 through Qt): scaling and gamma are applied in a shader. On machines without suitable OpenGL (for example some remote-desktop sessions) the app logs "Display: CPU fallback" and draws the same image on the CPU.

- **Freeze** (`Space`, toolbar or **View > Freeze display**): holds the image on screen so it can be inspected (zoom, pan, pixel readout) without saving anything. Only the display stops: the camera keeps acquiring, and averaging, reference refresh and recording carry on, so the status-bar rates stay live. An amber **FROZEN at** *time* bar over the image and a **FROZEN** badge in the status bar mark the held image; press `Space` again to return to the live view. **Save frame** saves the held image, and its `.txt` file records when it was frozen. **Set reference** still uses the live camera frame. With several cameras, each camera keeps its own frozen frame; **Switch to live capture** or turning a camera's processing off drops it.
- **Sliders and number boxes**: the mouse wheel over a slider or a number box scrolls the Controls panel and never changes the value. Drag a slider, click it, use the arrow keys, or type into the number box to change a value.
- **Raw difference** (toolbar toggle): shows |live − previous| of the raw camera frames and nothing else. Noise reduction, single field, filters, averaging, difference gain, stretch, gamma, flip and display tone are all bypassed while it is on (the button turns red and the view buttons grey out); turning it off returns to the chosen view and settings. The camera's own exposure and gain are left alone. Recordings are named `espi_rawdiff_*.avi`, and **Compare** shows the two raw frames.
- **Image navigation**: the toolbar's **Zoom** slider (drag or click it, or use the arrow keys) zooms from fit-to-window up to 64× and shows the zoom as a percentage, where 100% is the whole image fitting the window; **Fit** (`0`) and **1:1** (`1`) jump to those levels. The mouse wheel or trackpad on the image zooms around the cursor, and dragging pans.
- **Noise reduction** (Camera section): blends each new camera frame with the frames before it, in Raw, Previous and Reference (0 = off, 95 = strongest). It settles flickering sensor noise and leaves the speckle grain alone, because the fringes come from that grain. A still speckle image therefore looks almost the same at every setting. What changes is how much the picture boils, and a trail behind anything that moves. The number is how far the control is turned up, not the share of the previous frame kept: 10 is already about three frames of memory, and 95 is about twenty (the same cap as before). It used to read the number as that share, so most of the slider did almost nothing. **Auto stretch** then paints a quieter difference across the full brightness, so the fringe picture can look unchanged even though the status bar's Input range got narrower; use **Fixed gain** to see the amplitude. It is separate from **Average N** (which smooths the fringe picture) and the **Speckle filter** (which blurs the grain). High settings trail motion and soften **Previous**-view fringes, which are the change from one frame to the next. A Reference captured with it on is itself less noisy.
- **Default noise pipeline** (every camera, analog included): **Average camera frames, then subtract** is on with **Average N** 4, so camera and capture noise falls by √N before the difference instead of settling into a grey floor; **Ref. frames** is 16 and Reference view captures that averaged reference by itself when it has none, so the reference's own noise is not frozen into every difference; and the **Speckle filter** is **Oriented** at 11 px, which smooths along the fringes. A camera with a saved profile keeps the values it was left with; **Reset camera to defaults…** brings in the pipeline. The full frame rate needs Average N 1 (or frames-first off with a rolling average). Research and measurements: `docs/notes/espi-noise-and-capture-research.md`.
- **View**: **Raw** shows camera pixels for positioning (no ESPI processing or stretch; **Gamma** still applies). **Previous** shows frame-to-frame differences; **Reference** shows differences against a frame captured with `F` or **Set reference**. **Phase** is phase-shifting ESPI with the NI DAQ's piezo (below); its button appears once a piezo is assigned. **Average N** averages that many difference frames to reduce speckle noise: one image per N frames, or, with **Rolling average**, a running average that still updates every frame. With **Average camera frames, then subtract**, Average N averages the camera frames instead (one image per N frames; Rolling average does not apply) and the averages are subtracted, which cuts the camera noise itself by √N and keeps a steady change such as time-averaged fringes; averaging difference frames only smooths the noise into a grey floor. In Previous view, Frames back then counts averages; in Reference view, use Ref. frames of N or more so the reference is as quiet. **Ref. frames** (1–60, default 16) makes `F` average that many camera frames into the reference instead of keeping one, so a single frame's sensor noise is not frozen into every difference; the status bar counts the frames and the old reference stays in use until the new one is complete. **Ref. refresh** recaptures the Reference every N seconds so slow drift (air currents, heat) cancels; 0 keeps one reference until you press `F` (each refresh averages Ref. frames frames). **Frames back** sets which earlier frame Previous compares with (1 = the one just before); a larger number spans more time, so slow changes show instead of cancelling. Changing Noise reduction after `F` is flagged in the log and the Reference hint, since the reference was taken at the old setting. **Compare** (`C`) opens a window with three live images side by side, with its own Freeze and a Save that writes all three: in Reference view the stored reference, the current frame and their processed difference; in Previous view the earlier frame Previous subtracts (**Previous (N frames back)**), the current frame and the difference (the main image, averaging included). Changing the view while it is open switches what it shows.
- **Fringe enhancement**: **Outlier filter** (width in pixels, 0 = off) runs on every difference frame before averaging: a pixel further from its neighbourhood's mean than the neighbourhood's spread becomes that mean, so isolated spikes go and fringes stay (NI Vision's Lowpass rule, from the LabVIEW VI). **Speckle filter** (**Oriented**, the default; Gaussian; or edge-keeping Median capped at 5 px to keep the frame rate) with **Filter width** in pixels (default 11) blurs away pixel-scale speckle; keep it below the fringe spacing (0 = off). Oriented measures the local fringe direction (structure tensor of a reduced copy) and blurs along it, blending into a Gaussian where no direction stands out; on simulated difference fringes it matched or beat a Gaussian of the same width at every fringe spacing tried, most for dense fringes, at about 45 ms per 6 MP frame. **Invert** swaps bright and dark fringes. **Stretch clip** lets that percentage of the darkest and brightest pixels saturate so a few stray speckles don't flatten the contrast (0 = exact min/max). **Flip horizontally** (Display section) mirrors the image left to right in every view; saved frames and recordings match.
- **Scaling** turns difference values into brightness. **Fixed gain** multiplies every difference by **Difference gain** (×1–64; 42× by default, the LabVIEW ESPI 1.5 VI's Constant) and shows anything above 255 as white, as that VI did: the brightness does not follow each frame, and at 42× any difference of 7 grey levels or more is white. Lower it when noise shows as grey grain. **Auto stretch** maps each measurement frame's darkest and brightest difference pixels (after the clip) to 0 and 255; a constant difference image maps to all zeros. Analog cameras start in Fixed gain, the Blackfly and demo in Auto stretch. **Gain before averaging (LabVIEW order)** applies the gain to every frame (saturating), averages those, and multiplies the mean by **Average multiplier**, the VI's averaging maths; off, the raw differences are averaged and the gain is applied once. The status bar shows the range before and after scaling (before gamma). **Gamma** (Display section, its own control) is not a second stretch: it is a curve applied afterwards, in every view, that shifts mid-tones. Below 1.0 brightens dark fringes; above 1.0 darkens bright ones. With good scaling, leave it at 1.0.
- **Camera** sliders show direct values with exact-entry boxes and adapt to the camera's readable limits; the panel shows applied exposure/gain and requested/resulting FPS. Camera bandwidth and exposure determine the attainable frame rate.
- **Capture**: **Record AVI** writes the displayed image on a steady timeline (intermediate frames are skipped when acquisition outruns encoding; the last frame is repeated when it is slower); changing view mode or averaging starts a new file, and the log reports skipped frames and late encoder intervals. **Save frame** writes exactly what is on screen; an optional **Frame title** is added to the PNG's filename, and a title or notes also write a matching `.txt` file.
- **More fringe tools** (Fringe enhancement):
  - **Sensitivity floor** (grey levels): Auto stretch and Local normalization never span fewer, so a still scene's noise stays dark. Video-capture devices start at 30. **Calibrate noise (object still)** measures 2 s of a still scene's differences, in Previous or Reference view, and sets the floor to twice their peak.
  - **Noise threshold**: raw differences below it become 0, right after the subtraction.
  - **Subtract noise floor**: a still scene's difference never averages to zero, because each difference is an absolute value; it settles into a grey floor that Fixed gain shows as grain. **Measure noise floor (object still)** records each pixel's still-scene level (its mean plus one standard deviation, over at least 2 s and 16 images), and with the box ticked that map is taken off every difference after averaging and the speckle filter, so a still scene shows black. The map is per pixel because noise grows with brightness. It fits only the settings it was measured with (view, reference, exposure, gain, averaging and the filters before it); after a change the status bar asks for a new measurement and nothing is subtracted. Unlike Noise threshold it keeps faint changes that last across the average.
  - **Steady range** (Auto stretch only): the range shrinks only over this many seconds, so the contrast stops pumping; a growing range is followed at once.
  - **Even out beam brightness**: divides each difference by the local illumination so the centre of the laser spot does not dominate (off by default; it can amplify noise at the beam's edge).
  - **Peak hold window**: each pixel shows its largest difference within the last N seconds, so a steady vibration builds up in Previous view.
  - **Local normalization** (window in px): each pixel is compared with its neighbourhood's mean and spread, in place of Fixed gain or Auto stretch.
- **Display tone**: **Brightness** (adds grey levels), **Gain** (multiplies the displayed image) and **S-curve contrast** form one lookup table applied in every view before gamma; saved frames and recordings match the screen.
- **Collapsible sections**: click a Controls heading to hide or show that section. The choice is remembered between runs.
- **Interface size**: the **Interface size** slider (Controls panel, Display section) scales the whole window live, from 70% to 200% in 5% steps (100% is the standard look): text, buttons, sliders, check boxes, icons, docks, the status bar and dialogs. Drag and release (it applies on release, so the slider does not move under the pointer), type a value, or use **View > Interface size > Larger / Smaller / Reset** (`Ctrl++`, `Ctrl+-`, `Ctrl+0`; `Cmd` on a Mac). The size is remembered (`ui/scale_percent`). A size above 100% is lowered, with a log line, when the window's smallest size would not fit the screen. Use a smaller size on a small or high-resolution screen. The image is not scaled; it fills what the panels leave.
- **Pixels** (`P`, toolbar): opens a window with a square of the image (1×1, 2×2, 4×4 … 64×64 pixels; 8×8 at first, remembered) enlarged, each pixel a cell with its integer value written on it, shaded from black (0) to white (the largest in the square), with the square's min, mean and max above. In Previous and Reference view the values are the raw absolute difference in camera levels (0–255), before the noise threshold, gain, averaging and Scaling: 0 means no change, and movement raises them (with averaging before the difference on, the difference of the averaged frames). In Raw difference they are |live − previous|; Raw view shows camera levels. The square starts at the image center, is outlined in yellow on the main image, and moves to wherever you click the image. It refreshes ten times a second and has its own Freeze; the engine cuts it only while the window is open.
- **Shortcuts** (when not typing in a text field): `Space` freeze/resume, `S` save, `F` set reference, `C` compare with the reference, `P` pixel values, `R` reset last, `A` reset average, `Q`/Esc quit (Esc in a text field just leaves the field). The same list is in the View menu.
- **Tooltips**: hovering a slider, button, menu item or status readout explains what it does. A slider also shows its current value and unit, and a control with a shortcut names the key. Tips wait a moment so they do not flicker as the pointer moves, and they open beside the control so they do not cover the live image. The image itself has no tooltip.

### Which settings should I use?

Hover a processing control for what it does, when to use it, and a starting value. The same guide is under **Help > Which settings should I use?**. Three buttons at the top of **ESPI measurement** apply a starting point and leave exposure, gain, frame rate and recording alone, and a toggle under them switches to the LabVIEW flow. Each one also turns off the fringe-enhancement and display controls it does not use, so nothing carries over from the last preset:

- **Live preview** — aim the camera and see whether fringes form. Previous view, averaging off, noise reduction 0, speckle filter off, reference refresh 0, gray display. Switch to **Raw** to frame the object.
- **Measurement** — a still object against one reference. Reference view (press `F` once the object is still), an 8-frame block average (one clean image every 8 frames), Median speckle filter at 3 px, reference refresh 2 s, Auto stretch with a 0.5% clip, gray display.
- **Peak hold** — a vibrating object through the noisy analog camera (Sony XC-ST50 on the USB-Live2). Previous view; noise threshold 6 levels and a Median speckle filter at 3 px, both before peak hold, which would otherwise keep the loudest noise; peak hold window 1 s, so a steadily driven object's ring pattern builds up instead of flickering; Auto stretch with a 0.5% clip and a 1 s steady range; S-curve contrast 30%; gray display. It leaves the **Sensitivity floor** alone: analog cameras start at 30, and **Calibrate noise** (drive off) measures your own.
- **LabVIEW flow** (a toggle, off by default: every camera starts with the noise pipeline, which the VI did not have) — the processing of the LabVIEW ESPI 1.5 VI with its saved defaults, the known-good flow for that camera: Reference view with a reference captured at once (and whenever Reference has none), full frames, Fixed gain 42× applied to each frame before averaging (with Average N above 1, the VI's N + 1 frames divided by N), no camera-frame averaging, averaged reference, noise reduction, noise threshold, beam-brightness correction, speckle or outlier filter, peak hold, local normalization, stretch, display brightness/gain/contrast or invert. Exposure, gain, frame rate, recording and the flip keep their values. Turning it off puts back the settings you had before; changes made while it is on are dropped. Each camera keeps its own state. See `docs/labview/README.md`.

**Ref. refresh** trades drift cancellation against seeing slow motion: 2 s removes air and heat drift, and also any real motion slower than that. Use 0 and press `F` for one fixed before/after.

Noise reduction, averaging and the speckle filter are different steps. Noise reduction blends camera frames before the difference and keeps the speckle (it trails motion). Average N blends camera frames before the difference by default (one image per N frames), or difference frames with Average camera frames off (block: one image per N frames; rolling: full frame rate, with a lag). The speckle filter blurs each difference image; keep its width below the fringe spacing.

Processing order for Previous and Reference views: noise reduction → (frame average) → difference (N frames back) → noise threshold → beam brightness → outlier filter → average → speckle filter → noise floor → peak hold → fixed gain, stretch or local normalization → invert → brightness, gain and contrast → gamma. Phase view: piezo phase steps → wrapped phase → minus the reference phase → sine/cosine filter. The frame average runs only with **Average camera frames, then subtract**, which moves Average N there, and the noise floor only with **Subtract noise floor**. With Gain before averaging, the fixed gain moves to just before the outlier filter and Average multiplier scales the average. Raw applies noise reduction, display gamma and the display brightness, gain and contrast, without scaling.

Output goes to `output/logs/`, `output/frames/` and `output/recordings/`. Recordings and saved frames carry the camera's serial number in the filename (for example `espi_raw_12345678_<time>.avi`).

### Several cameras

A **Cameras** section sits at the top of the Controls panel. **Display** names the camera shown in the window and, with several cameras, picks which one. When more than one FLIR camera is connected, each camera also has a **Process** checkbox: a checked camera keeps acquiring, processing and (when Record is on for it) recording while another camera is displayed. The displayed camera always processes, so its checkbox is locked on; choosing an unchecked camera in **Display** turns it on. Each row shows that camera's processed frame rate and `REC` while it records.

Each camera has its own settings: exposure, gain, frame rate, noise reduction, view mode, reference frame, averaging, fringe and display options, and its own Record state. The settings (not recording, the reference or the averages) are kept between runs; see **Camera profiles and presets** below. The controls, toolbar and shortcuts always act on the displayed camera. Unchecking **Process** stops that camera (finishing its recording and releasing it) but keeps its settings for the next time; its reference frame and running average start fresh. At startup only the first camera that opens is processed. Log lines from each camera start with its serial number, and an error in one camera turns only that camera off.

Several 6.3 MP cameras streaming at once can exceed one USB 3 controller's bandwidth; watch each row's frame rate, and lower the frame rate or put the cameras on separate controllers if it drops. `--demo --demo-cameras 3` simulates three cameras for trying this without hardware.

### Camera profiles and presets

Each camera's settings form its own **profile**: exposure, gain, frame rate, the view mode and every processing and display control, including the LabVIEW flow's on/off state and the values it keeps to return to. A change made while one camera is displayed never reaches another; with several cameras the Camera section starts with **Settings of** *camera*, and **Display** switches between the cameras' profiles.

- **Saved between runs.** Each profile is written to the program's settings store (QSettings: the registry on Windows, a preferences file on macOS and Linux) about a second after it stops changing, when you switch cameras and on close, and is restored the next time that camera is connected, before it opens; the log names the restored exposure, gain, frame rate and view. FLIR cameras are keyed by serial number (`profiles/flir/<serial>`), analog capture devices by USB ID and name (`profiles/capture/<vid>-<pid>/<name>`, since their `video N` number is only the enumeration order), iPhones by the serial taken from their UDID (`profiles/iphone/<serial>`), and demo cameras have their own namespace (`profiles/demo/<serial>`), so demo values never land on a real camera, not even after **Switch to live capture** (the live camera gets its own saved profile, or its defaults).
- **Not saved:** recording (a camera never starts recording), window layout, interface size, zoom and which Controls sections are open.
- **Defaults.** A camera with nothing saved starts from exposure 8000 µs, gain 0 dB, 30 fps and the default noise pipeline, with the LabVIEW flow off (the analog camera used to start in it). A camera with a saved profile starts from its last values instead, so a camera PC keeps the processing it was left with. Exposure, gain and frame rate are still clamped to the camera's limits. **Reset camera to defaults…** (Camera section, with a confirmation) puts the displayed camera back and clears its saved profile.
- **Presets** (Camera section): **Save as…** stores the displayed camera's profile under a name (`presets/<name>`, letter case ignored; an existing name is replaced only after a confirmation, and the camera model is recorded); pick a preset and **Apply** it to the displayed camera only, which keeps the result as its profile; **Delete** removes one after a confirmation. A preset from another camera model applies its processing values in full and fits exposure, gain and frame rate into this camera's limits; the log lists each clamped value and ends with `Preset applied: <name> to <camera>`. The built-in **Live preview**, **Measurement** and **Peak hold** buttons are not in that list: they change processing only, never exposure, gain, frame rate or the LabVIEW flow.
- Loading is tolerant: unknown keys (such as `palette` and `clahe` from older builds) are ignored, and a wrong-typed or out-of-range value falls back to the default and is logged (`profiles.py`).

### Analog camera (Sony XC-ST50)

The XC-ST50's composite video goes through a Hauppauge USB-Live2 into the PC, and the stick appears in the camera list as **Hauppauge USB-Live2 (video N)**. Close WinTV and Hauppauge Capture first: the stick serves one program at a time. Exposure, gain and frame rate are set by the camera's own switches, so those controls are disabled for it, and the status line shows the measured capture rate. It shows full interlaced frames by default, as the LabVIEW VI did; **Single field (interlaced camera)** shows only one of the two fields (repeated to full height), which removes the 1/60 s between fields at the cost of half the vertical detail. Differences compare rows woven the same way, so the offset rarely matters for ESPI. It starts in Reference view with Fixed gain 42× and the default noise pipeline: four camera frames averaged before the difference (which also averages the stick's capture noise and line jitter), a 16-frame automatic reference and the Oriented speckle filter. Fixed gain because Auto stretch would blow the capture noise (3–5 grey levels) up to full-contrast grain. The **LabVIEW flow** toggle gives the known-good LabVIEW ESPI 1.5 processing with that program's saved defaults instead (Fixed gain 42×, a one-frame automatic reference, no averaging or filters). The viewer reads the stick's raw YUY2 brightness bytes (Media Foundation on Windows, V4L2 on Linux) instead of converting to colour and back, which removes about ±1 grey level of conversion error at the same grey-level scale; if that path does not check out it uses the colour conversion as before, and `ESPI_ANALOG_LUMA=bgr` forces it. `python scripts/check_analog_luma.py` shows which path is used and compares the two. Images look about 12 % wide because NTSC pixels are not square; they are not resampled. Expect coarser fringes than with the Blackfly. Wiring, driver settings and details: `docs/camera/sony-xc-st50-usb-live2.md`.

A laptop's built-in camera (USB IDs in `capture_models.BUILT_IN_CAMERAS`, or names such as "Integrated Webcam", "Integrated Camera", "IR Camera" or "FaceTime") is left out of the list entirely: it is never shown, opened or reported, and the log notes it as `Ignoring the built-in camera …`.

Other video devices (webcams, other capture sticks) are listed as **not yet supported** and are never opened unless you choose one. When you switch one on, it runs as delivered, and the viewer files a GitHub issue (label `camera-support`) with what the device reports, once per device type. A copy without a feedback token saves the report to `output/logs/camera-report-*.md` and shows a **Report this camera** button instead.

### Frequency generator and piezo (NI DAQ)

**Devices → Frequency generator and piezo (NI DAQ)…** drives the specimen excitation and the reference piezo from an NI multifunction DAQ such as the USB-6251. Assign each role its own output: the frequency generator to an analog output (a sine) or to a counter (a 0–5 V square wave on a chosen PFI terminal), and the piezo driver to an analog output. The piezo either holds a voltage, with **Step −/+** buttons for manual phase steps, or follows the generator with a sine at the same frequency and a set phase; the two analog outputs share one sample clock, so that phase is exact. Each role has a **Safety limit** in volts that no setting may exceed. **All outputs to 0 V** stops everything, and the outputs also go to 0 V on an error and when the program closes. Volts are at the DAQ, before your amplifiers: the DAQ cannot drive a shaker or piezo directly. Frames are not synchronised to the generator's drive yet; the piezo's phase steps are (next section).

### Phase view (phase-shifting ESPI)

With the piezo driver assigned, the **Phase** view steps the reference piezo between frames and shows each pixel's phase change since the phase reference, wrapped to one fringe: mid-grey is no change, black to white is 2π, and unlike subtraction fringes the ramp's direction shows the sign of the deformation. Once **Apply** in the DAQ window has saved settings that assign the piezo driver, the piezo is picked up whenever that device connects (at startup, or from the DAQ window): the displayed camera switches to the Phase view and its button appears, and the piezo follows the displayed camera. Opening the DAQ window alone never drives the piezo. Each step: the DAQ holds the piezo at the **Voltage** plus N × **Step** (a quarter wave once calibrated), the next **Settle** frames (default 2, plus one after the return to step 0) are dropped because they were exposed while it moved, and Average N frames are averaged (with Average camera frames on). **Phase steps**: **5-step (Hariharan)** (default) tolerates a step that is not exactly 90° (1° phase error at a 75° step in simulation, against 7.5° for 4-step) and measures the step it made, shown in the status bar; **4-step** is faster. The phase difference is filtered as sine and cosine (**Phase filter**, default 9 px), weighting strongly interfering speckles, so the filter never blurs across the jump from white to black. The first complete set is the phase reference; `F` takes a new one. **Calibrate phase step** (keep the object still) measures the step over five 5-step sets and sets the DAQ's step voltage for 90°, saved with the DAQ settings. Every step stays inside the piezo's safety limit; 0 V, an error or a disconnect stops the stepping. In dummy mode with the simulated device, the synthetic camera becomes a speckle interferometer that follows the simulated piezo (72° per 0.05 V, so calibration has something to correct).

The device work goes through [pyLabLib](https://pylablib.readthedocs.io/en/latest/devices/nidaq.html)'s `NIDAQ` class (`pylablib-lightweight`, without its Qt and other extras) on NI's `nidaqmx` package, both in `requirements.txt`. The NI-DAQmx driver comes from ni.com and runs on Windows and Linux only. Without it, or on a Mac, the window offers only a **Simulated device (no hardware)**, marked in red, for trying the controls. Hardware research and the synchronisation design are in `docs/notes/ni-usb-6251-integration.md` (PR #68).

### iPhone camera (USB)

An iPhone running the **ESPI Camera** app (`ios/ESPICamera/`, installed from TestFlight) is a camera source over its USB cable: frames arrive uncompressed (8-bit luma), with exposure, ISO, focus and white balance locked. On Windows, install iTunes from apple.com once for the Apple Mobile Device Service. Plug the phone in, unlock it, tap **Trust** and keep the app on screen; each back camera is listed as its own camera (an iPhone 16 Pro Max shows **iPhone Ultra Wide 0.5× (USB)**, **iPhone Wide 1× (USB)** and **iPhone Telephoto 5× (USB)**), and a phone with one back camera shows **iPhone (USB)**. Only one lens streams at a time: choosing another turns the first one off (its settings are kept). Exposure and Gain (as ISO above the phone's lowest) drive the phone, and an **iPhone** section sets its frame rate, frame size, crop, send-rate cap and focus, so nothing needs touching on the phone. USB 2 phones manage about 1920 × 1080 at 15 fps. It is a rolling-shutter colour camera with built-in noise reduction, so treat it as a qualitative viewer. **Capture** can switch it to **Bayer RAW**: stills of one colour plane (red, green or blue) of the sensor's own data at about 5–10 fps, without the phone's noise reduction and tone mapping; ESPI Live carries those frames at full precision (float32 grey levels) until the final 8-bit picture. Setup, bandwidth, limits and the link protocol: `docs/iphone/README.md`; building and TestFlight: `ios/README.md`.

### Demo mode

If no FLIR camera or recognised capture adapter is detected (or PySpin is unavailable and no adapter is connected), startup offers **dummy/demo mode**, and `--demo` starts it directly without touching a camera. It opens the same windows with a **simulated ESPI signal**: an ideal sensor (no shot, read or fixed-pattern noise; brightness proportional to exposure and gain, 8-bit, clipping at 255) looking at a speckle interferometer whose specimen is a drumhead, an ideal circular membrane clamped at its rim, so every processing step runs on a signal whose correct result is known. The **Simulated object** control (Camera section, demo cameras only) chooses **Still**, **Slow deformation** (a pad presses the drum in to 8 fringes and releases it every 12 s; the default), **Vibration** (drum mode (1, 1) at 1000 Hz, 5 J0 fringes) or **Follow DAQ** (the NI DAQ window's generator drives the drum's modes: 628 Hz (0, 1), 1000 Hz (1, 1), 1340 Hz (2, 1), 1441 Hz (0, 2) …; the Simulated device works). The DAQ piezo moves the simulated reference mirror in every case (1500 nm per DAQ volt), and the **Reference piezo (triangle, decorrelation)** checkbox ramps it with a 1 Hz, 1.2 µm triangle wave as a reference-beam piezo does on the bench, so Previous view shows a vibration's |J0| fringes with a white nodal line instead of a black image. Vibration is averaged exactly over each exposure, so a fractional number of drive cycles per exposure flickers as on a real camera. See `docs/notes/simulated-espi-signal-design.md`. A persistent **DUMMY MODE ACTIVE** banner appears in the viewer and in saved frames and recordings, which also get `dummy_` filename prefixes. **Switch to live capture** retries camera detection without restarting: if no camera is available, demo continues; if one connects, measurement baselines reset to Raw view and any demo recording stops so synthetic and live frames never share a file. Demo mode is for interface and processing checks, not camera-performance measurements.

The app temporarily requests 1 ms timer resolution while running so demo pacing tracks the requested FPS; this can increase power use.
