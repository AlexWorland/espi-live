# AGENTS.md

Guidance for AI coding agents and developers working in this repository. See `README.md` for usage and the full layout.

## Overview

A live viewer for a FLIR Blackfly (BFS-U3-63S4M-C) Mono8 camera used for ESPI measurements (plus the analog Sony XC-ST50 through a Hauppauge USB-Live2 capture stick, read with OpenCV), written in Python with PySpin/Spinnaker, OpenCV, NumPy and PySide6 (Qt). An iPhone running the ESPI Camera iOS app (`ios/ESPICamera/`, Swift, distributed through TestFlight) is also a camera, over its USB cable through usbmuxd. It must stay cross-platform (Windows camera PC, macOS and Linux). The camera runtime is a Windows PC (Python 3.10 with PySpin, SDK 4.2); the macOS checkout is for editing and camera-free `--demo` runs.

## Commands

```sh
./run.sh --demo                                    # Qt UI, synthetic video, no camera or PySpin
./run.sh                                           # try a real camera; offers demo mode if none found
PYTHONPATH=src python -m espi_live --check         # import everything (Qt, engine, PySpin if present), no window
PYTHONPATH=src python -m unittest discover -s tests   # camera-free tests
python scripts/run_tests.py                        # same suite in parallel (one worker per CPU core), merged coverage, 100% gate; --no-coverage skips it, -j N sets workers
PYTHONPATH=src QT_QPA_PLATFORM=offscreen python -m coverage run -m unittest discover -s tests && python -m coverage report   # must stay at 100% (.coveragerc)
python -m py_compile src/espi_live/*.py            # required check after edits (no display or camera needed)
```

- `.venv` (Python 3.14) holds numpy, opencv-python and PySide6 from `requirements.txt`. PySpin is imported lazily by `camera.load_pyspin()`.
- PySide6 is required: there is no other front end (the legacy Tk UI was removed). Without it the program exits with a message.
- Windows camera PC: `scripts/windows/SETUP AND START ESPI.bat` validates and installs dependencies (including PySide6), then launches the app with `PYTHONPATH=src`.
- Do not run camera-acquisition code without the user's direction; the camera may be absent or in use. `--demo` and `--check` never open a camera.
- Outputs go to `<project>/output/{logs,frames,recordings}/` (`paths.OUTPUT_DIR`, independent of the working directory; next to the executable in PyInstaller builds); demo files are prefixed `dummy_`.

## Architecture (`src/espi_live/`)

| Module | Role |
|--------|------|
| `guide.py` | Locates the bundled `user_guide.html` from source or a packaged build and supplies an error page when it cannot be read |
| `paths.py` | `PROJECT_ROOT`/`OUTPUT_DIR` (frozen-build aware), `timestamp()`, `output_folder()` |
| `processing.py` | **Deep frames**: a source with more than 8 bits (the iPhone's RAW mode) hands the engine float32 frames in 8-bit-equivalent grey levels (`is_deep`, `DEEP_DTYPE`; black 0, full scale 255, fractions and negatives kept); every step up to the final scaling accepts them and keeps the precision, `to_uint8` makes the shown/saved/recorded picture, and a uint8 frame takes the unchanged 8-bit path. `VIEW_MODES` (Raw, Previous, Reference, Phase), `SMOOTHING_METHODS` (Oriented, the default; Gaussian; Median), `oriented_smooth` (the Oriented speckle filter: a light isotropic blur, then a long blur along the fringe direction from the structure tensor of a 1/`ORIENTATION_SCALE` copy, blended into a Gaussian where coherence is low; `_line_blur` does the diagonals with shifted adds because a diagonal `filter2D` costs ~60 ms at 6 MP), `ESPIProcessor` (difference with `frames_back` history, averaging with an optional scale, `average_frames` (block mean of camera frames before the difference), `reset_previous`, the reference and its N-frame `ReferenceCapture`), `apply_gain` (fixed gain, saturating), `reject_outliers` (NI Vision Lowpass rule), `stretch_levels`/`apply_levels` and `RangeTracker` (stretch with sensitivity floor and steady range), `NoiseCalibration`, `NoiseFloorMap`/`subtract_floor` (per-pixel still-scene floor, mean + `FLOOR_SD_MARGIN` sd), `PeakHold` (sliding-window maximum), `local_normalize`, `even_out_brightness`, `display_lut` (display brightness, gain, S-curve), `normalize_min_max`, `apply_display` (the one definition of display tone: gamma, always grayscale), `display_rgb_table` (same gray values as a GPU table), `watermark_demo` |

**Engine threading.** The front end chooses the source on its own thread before `start()` (`open_camera()` or `use_demo()`, so it can ask about demo mode), or calls `open_on_start(after=old_engine)` so the worker opens the camera itself (used when a camera is turned on while the window runs); after that, every PySpin call (grab, node writes, readback, close, live switch) happens on the engine's worker thread. A `CameraSession`, `CaptureSession` or `IPhoneSession` must only ever be used by one thread at a time (an `IPhoneSession` also runs its own reader thread internally). The UI talks to the engine only through `update_settings(**fields)`, `request(action, **payload)` (`save`, optionally with a frozen display's `packet` and `frozen_at`; `save_compare` with a `ComparePacket`; `reference` (one frame, or starts averaging `ref_frames` frames), `reset_previous`, `reset_average`, `switch_live`, `camera_command` (phone-only settings for a source with `send_command`), `drive` (a `daq.Drive` for the demo source; ignored by cameras)), `latest_packet()`, `status()`, `set_square(size, center)`/`latest_square()` (the Pixels window's `SquarePacket`, cut from the raw difference every 0.1 s only while asked) and the `events` queue (`camera_identity`, `camera_limits`, `camera_settings` (settings an iPhone reports, from `take_settings_update()` at each readback), `camera_report` (unrecognised video device: a `camera_reports.Report`), `record_off`, `switched_live` (payload: every detected `CameraInfo`), `switch_failed`, `open_failed`, `fatal` (payload: error message plus the report's error ID), `stopped`). Never touch Qt objects from the worker. The error reporter's `ErrorReportWorker` posts `("outcome", Outcome)` events the window drains; capture never blocks any thread.

**Several cameras.** Each camera is a `Channel` with its own `Engine` and worker thread, so settings, reference, averaging and recording are per camera. The Qt `MainWindow` owns the list, displays `self.current` (its `engine` and `camera_identity` properties are the displayed channel's, which every control uses) and keeps the displayed channel processing. Sessions share the PySpin `System` through `acquire_system()`/`release_system()`, because `System.ReleaseInstance()` fails while any camera is still referenced; never call `GetInstance`/`ReleaseInstance` directly in package code. An error in one channel stops only that channel; the window closes when none is left.

**Camera profiles.** Each channel's settings and LabVIEW-flow state are its profile, and nothing a control does while one camera is displayed may reach another: every control writes only `self.engine`, `_load_settings` shows a camera's values without sending them (its limits are applied with `_apply_limits(..., quiet=True)`, because a clamping range would otherwise send the previous camera's value to the new one), and per-camera state lives on the `Channel`, never in globals. Profiles persist in QSettings through `profiles.ProfileStore`: `run()` builds one store, restores each camera's saved profile before it opens (`restore_channel`, logged with its camera values), and the window writes a profile once it settles (`profile_timer`, `PROFILE_SAVE_MS`), on a camera switch and on close. A camera with nothing saved must start from exactly `default_profile` (exposure 8000 µs, gain 0 dB, 30 fps); a saved profile starts it from its last values. Never persist `record`. Demo channels keep the `demo/` namespace, and **Switch to live capture** gives the live camera its own saved profile or its defaults, never the demo's values. Named presets (`presets/`) apply to the displayed camera only, with `clamp_to_limits` against its limits, and are saved as its profile; the built-in `PROCESSING_PRESETS` stay separate (processing only, not in the presets list). **Reset camera to defaults…** forgets the displayed camera's profile. Keep `profiles.py` free of Qt, and keep its `RANGES` containing every control's range (a test checks it) when a control's range changes.

**Frame flow.** Each worker iteration: grab (`CameraSession.grab(100)` or `simulation.DemoSource.next_frame` on a fixed schedule, after `set_object(demo_object)`) → apply changed camera settings (rate-limited to 0.1 s; readback every 1 s) → Raw passes the frame through and still carries the display gamma (no stretch); Previous/Reference run (with `average_frames_first`: `average_frames`, a block mean of N camera frames; nothing more until it is complete) → `difference` (Previous: the frame `frames_back` frames earlier) → noise threshold → optional `even_out_brightness` → (LabVIEW order: `apply_gain`) → `reject_outliers` → `average` (block; LabVIEW order sums N + 1 frames, × `average_multiplier` ÷ N) or `rolling_average` (skipped with `average_frames_first`) → `smooth_speckle` → (`floor_subtract`: `subtract_floor` with the `NoiseFloorMap` measured by the `measure_floor` action, only while its `floor_key` matches) → `PeakHold` → `local_normalize`, or Auto stretch (`stretch_levels` → `RangeTracker` floor and steady range → `apply_levels`), or `apply_gain` (Fixed gain, unless already applied) → optional invert → `display_lut` (every view) → flip → demo watermark → publish an immutable `FramePacket` (newest wins; older ones are dropped) → feed the recorder → handle queued actions. `Settings.raw_difference` (the Qt toolbar's **Raw difference** toggle) overrides all of this: after the grab it skips single field and noise reduction and publishes `raw_difference(live, previous)` (`cv2.absdiff`, no gain, stretch, gamma, display tone or flip; demo watermark only) as mode `RawDiff`, and turning it on or off resets the processing state. A mode change resets averaging; `average` returns `None` until N frames accumulate (`rolling_average` returns every frame). Reference auto-refresh recaptures the baseline every `ref_refresh_s`.

**Phase view.** With `mode == "Phase"` (and no Raw difference) each frame goes to `Engine._phase_frame` instead: frames are collected per phase step (Average N per step with `average_frames_first`), and when a step is complete the worker calls `PiezoStepper.move` for the next one (blocking until the DAQ thread has written it) and the next `phase_settle_frames` frames are dropped. A complete set → `wrapped_phase` → minus the phase reference → `filter_phase` → `phase_image`, published with gamma 1 and no display tone (flip and watermark still apply); no comparison is built. Without a stepper (or with one that breaks a rule) the camera frame is shown and the hint says why; a failed move drops the stepper and sends `phase_stopped`. A different stepper object (attached, removed, recalibrated) restarts the set and takes a new phase reference. The window attaches the stepper to the displayed camera's engine only (`MainWindow._attach_stepper`, also on a camera switch), and a stepper arriving where there was none selects the Phase view.

**Display.** A `FramePacket` holds the Mono8 image plus the display gamma still to apply (`sequence, image, gamma, mode, demo`); the display is always grayscale. `GLImageView` uploads it as an R8 texture (with mipmaps) and a fragment shader maps it through a 256-entry RGB table from `display_rgb_table`; scaling, zoom and pan are GPU work. Saving and recording call `FramePacket.render()` → `apply_display`, so files match the screen exactly (a test enforces this). `CpuImageView` is used when an OpenGL 3.3 core context is unavailable (for example some remote-desktop sessions). **Freeze** (`MainWindow.set_frozen`, Space) is display-only: the window holds the packet it last drew on the displayed `Channel` and stops drawing new ones, while the engine keeps acquiring, processing and recording; Save sends the held packet, and the amber banner over the image, status badge and button mark it. A frozen demo frame is dropped on `switched_live`, so it can never outlast the dummy-mode indicators.

**Interface size.** `MainWindow.set_ui_scale(percent)` rescales the whole window live (Controls > Display slider, applied on release; View > Interface size; Ctrl++/Ctrl+-/Ctrl+0; remembered in QSettings and applied before any widget is built). `qt_app.apply_app_scale` scales the application font (so every text, tooltip, menu and dialog follows), replaces the application style with `ScaledStyle` (a `TooltipDelayStyle` that multiplies the `SCALED_METRICS` pixel metrics: margins, spacing, check/radio indicators, slider handles, scroll bars, icons, docks) and delivers the posted font-change events before returning, because existing widgets only get the font through them. Qt does not re-measure what the program fixed in pixels, so `_rescale_widgets` re-applies those: lengths registered with `MainWindow._sized(setter, *px_at_100)` and style sheets with `MainWindow._styled(widget, style_at_100)` (permanent widgets only), `SliderSpin.rescale`, the status buttons (`_arm_status_button` remembers its arguments; icons are repainted at the new size), `_fit_controls_width` and `_fit_status_bar`; `FixedLabel` re-measures itself on `FontChange`. A dock title keeps a stale font unless its dock holds an explicit font that differs from the application's (`nudged_font`). An interface size above 100% is stepped down until `minimumSizeHint` fits the screen (`_limit_scale_to_screen`, also on a screen change), so the window cannot leave the screen; 100% and below are never changed by it. The image views are not scaled.

**Demo mode.** `simulation.DemoSource` renders a simulated ESPI signal on an ideal sensor (see its row above); in the Phase view the dummy frames come from `phase.DemoInterferometer` instead, which follows the piezo's phase steps; `Settings.demo_object` (the Qt **Simulated object** control, shown only for demo channels) chooses what the drumhead does, and the window forwards the DAQ window's applied `Drive` to every channel (`MainWindow.set_daq_drive` → `Channel.set_drive` → the `drive` request; `DaqDialog.poll` also runs from `_poll_status` while the DAQ window is hidden, and zeroing, a failure or a new connection send `Drive()`). `watermark_demo` stamps "DUMMY MODE ACTIVE" into every published frame, so it appears on screen, in saved frames and in recordings, and the Qt UI also shows a red banner, title and status badge. Demo data must never be mistakable for camera data. The "Switch to live capture" retry must leave the synthetic stream running on failure, and on success reset measurement state and stop any demo recording.

## Rules

- Before changing PySpin, camera lifecycle, node-map or image-buffer code, read `docs/camera/README.md` and the files it points to: `spinnaker-pyspin.md` always, `blackfly-bfs-u3-63s4m-c.md` for model-specific settings, `acquisition-and-performance.md` for streaming, ROI, pixel format, frame rate, preview latency, recording or triggering.
- Verify a node is readable/writable before writing it and clamp numeric values to device limits (`set_enum`/`set_bool`/`set_float` wrapped by `try_setting` do this). Release every `GetNextImage` result in a `finally` (`CameraSession.grab` does), and `.copy()` `GetNDArray()` data that outlives the image. Preserve safe lifecycle handling on errors.
- Don't change default exposure (8000 µs), gain (0 dB), frame rate (30 fps) or recording behavior without calling out the impact. Don't assume the displayed rate equals the camera's acquisition rate.
- Keep processing, camera and recording code free of GUI imports so the front end and the tests share it. Keep display tone defined only in `processing.apply_display`; the display is always grayscale (no color palettes).
- Sizes in the Qt front end follow the interface size: never hard-code a pixel length for a widget that lives as long as the window (`setFixedWidth(130)`, `setContentsMargins`, `padding:8px` in a style sheet). Register it with `_sized`/`_styled`, use `ui_scale.px` for a dialog or a widget built on demand, and re-measure anything computed from font metrics when the font changes (`FontChange`, or `_fit_status_bar`/`_fit_controls_width`). Check a new control at 70% and 200% (`window.set_ui_scale`). Leave the image views and 1px borders unscaled.
- Keep it cross-platform: no platform-only GUI SDKs; guard OS-specific calls. The builds run Python 3.10 (Windows) and 3.12, so keep the package's syntax compatible with 3.10 (no `except*`, no PEP 701 nested same-quote f-strings; check with `py_compile` under 3.11/3.12 when unsure). The GPU path needs only OpenGL 3.3 core through Qt; keep the CPU fallback working.
- NI DAQ outputs: every pyLabLib/`nidaqmx` call runs on the `DaqController` thread; never call them from the UI or an engine (an engine steps the piezo only through `DaqController.move_piezo`). A piezo counts as configured only once Apply has saved settings that assign it (`MainWindow._saved_piezo`) or in this session's applied settings: merely opening the DAQ window (whose defaults name AO 1) must never attach it or start stepping. `MainWindow.poll_daq` is the only reader of the controller's events; it passes each one on to the DAQ window. Every path that stops using an output (zero, close, error, exit) leaves it at 0 V, and no setting may exceed its role's safety limit; the piezo driver, including phase steps, never goes below `daq.PIEZO_FLOOR_V` (0 V). The simulated device must stay visibly marked. Tests run pyLabLib's real `NIDAQ` on `tests/fake_nidaqmx.py`; they never need NI hardware or the driver.
- Keep `logs.py` and `error_reports.py` GUI-free (the front ends drive them) and camera-free. The repository is public: every automatic report is public, so route any new report text through `scrub`, log expected operating conditions at WARNING only (extend the tested `EXPECTED` allowlist for new ones), and never change what the `ESPI-ERR-v1` fingerprint hashes without bumping the version prefix (see the `error_reports` module docstring). Capture must never block a thread or raise into it, and an error inside the reporter is logged, never reported.
- Don't reintroduce OpenCV HighGUI windows: mixing them with another toolkit caused fatal Windows crashes.
- Every function needs a docstring in the existing `Args: ... / Returns: ...` format.
- Put tentative work in `experiments/`; promote it into `src/espi_live/` only when it becomes the intended maintained implementation. Use descriptive, purpose-based filenames; date-based names belong in `archive/`.
- Store recordings under `output/recordings/` and still frames under `output/frames/`. Don't commit generated media.
- Keep Windows and Bash helpers in `scripts/` and update their paths whenever a referenced file moves (they resolve `third_party/` and `src/` relative to the repo root).
- Updates must never start the new build while the camera is open: the Qt front end installs and relaunches only after the engine has stopped (`qt_app.finish_update`). Keep the release archive names, the `Release from …, build N. Build log:` line that starts the notes CI adds to each release, `build-info.json` and `_build_info.py` fields in `build-binaries.yml` in step with `updater.py` and `feedback.py`, and the Windows/Linux program folder too: PyInstaller onedir with `--contents-directory _internal-<build>` (`updater.CONTENTS_PREFIX`), holding only the executable and that folder (the smoke test checks it; the updater refuses anything else). A running Windows program's executable and loaded DLLs can be renamed but not overwritten or deleted, so never give two builds the same library folder name, and never make the updater touch the running build's folder. Startup cleanup deletes only update leftovers, other builds' library folders and files it has verified as single-file builds of this program; never `output/` or token files. `build-info.json` lists the archives' SHA-256 under `archives`; never put a folder archive under `sha256`, the key the single-file builds (build 6 and earlier) read, whose updater would put the folder where their executable was. A public release must always carry `build-info.json` (the updater reads `/releases/latest`), which is why published drafts are held as drafts until the archives are attached; the updater orders builds by the `build` number in that file, never by tag name.
- Tokens baked into builds are extractable by anyone with a binary, and the binaries are public: keep each to the minimum scope (`UPDATE_TOKEN`, optional now that the repository is public, Contents: read; `FEEDBACK_TOKEN` Issues: read & write; `LOGS_TOKEN` Contents: read & write on the private `espi-live-logs` repository only, never on this one: a log token that can reach this repository would let anyone with a binary push code; `CAPTURES_TOKEN` the same on the private `espi-live-captures` repository only, and since images cannot be scrubbed it can read every upload). The release build fails when `FEEDBACK_TOKEN` is empty, because the feature-request form files issues from the app and has no browser fallback. Never bake in AI or write-to-code credentials. Changes sent from Open in Codex therefore travel as issues, and only `codex-change.yml` writes code (a new branch and a pull request, never `main`); keep `changes.py`'s issue format and `codex-change.yml` in step, and keep the program's guide for Codex (`codex.GUIDE`) telling Codex to send only after the user approves, and never through git. Copilot runs only in Actions (`COPILOT_PAT`), and so does the roadmap write: `PROJECT_PAT` (projects: write) is used only by `add-error-to-project.yml`, never by a build. In workflows, pass issue text through `env:`, never `${{ }}` inside `run:`.
- Don't add a virtual-environment or dependency-management system (pyproject, lockfiles) unless asked.
- Keep `README.md` accurate when layout, entry points or setup change, and add a `CHANGELOG.md` entry for user-visible changes.
- After edits, run `python -m py_compile` on the changed files and the tests. Keep line coverage at 100% (`coverage report` fails below it, and so does the release workflow): add tests with new code, and don't use `# pragma: no cover`. Tests must never open a camera, touch the network, write to the real `output/` folder or block on a dialog.

## Git

- This repository is public (GPL-3.0, `LICENSE`). Never commit the FLIR SDK, other people's scripts or personal documents to it: once pushed, they stay reachable through pull-request refs even after a history rewrite. SDK files go in the private `espi-live-sdk` repository (Git LFS there).
- Work in a clone of this repository. Clones of the private `espi-live-archive` (the history before the repository went public) still hold the SDK in their history: never push their branches here or add this repository as their remote. Before pushing, `git log --oneline origin/main..HEAD` must list only your own commits. This repository has no Git LFS files, so if a push starts uploading LFS objects, stop it at once.
- `.gitignore` excludes `.venv/`, `__pycache__/`, `.DS_Store`, `.omc/`, `output/`, `build/`, `dist/`, `research/` (never push it), `third_party/`, Office lock files, and large binaries (`*.avi`, `*.zip`, `*.whl`, `*.dmg`, `*.tar.gz`, `*.pptx`). Don't force-add them.
- CI checks out `espi-live-sdk` into `third_party/`, fetches only the LFS files each platform needs (`git lfs pull --include`) and caches them, since LFS bandwidth is metered; `setup-python` caches pip downloads (`cache: pip`). Keep that behavior when editing `build-binaries.yml`.
- The Linux build installs FLIR's Spinnaker 4.4 `.deb` packages, whose install scripts expect an interactive desktop. Keep these workarounds in `build-binaries.yml`: the `debconf-set-selections` preseed of `libspinnaker/accepted-flir-eula` (without it libgentl's preinst exits 2 because it cannot show the EULA); `sudo env -u SUDO_USER` for that `apt-get install` (the preinst asks the sudo user for analytics consent under `set -e`, which exits 30 without a terminal and cannot be preseeded because the script resets the answer; with no user found it skips the question, and libspinnaker's postinst skips its analytics ping); `spinupdate` (`_PySpin` links against `libSpinUpdate`); and `libavcodec60 libavformat60 libavutil58 libswscale7` (FFmpeg, which `libSpinVideo` links against but does not declare).
- Check Linux build changes locally before pushing them: run the job's commands in an `ubuntu:24.04` container (`docker run --platform linux/amd64`) as a non-root user calling `sudo`, through `ldd` on `/opt/spinnaker/lib/*` and `_PySpin` (no `not found`), `import PySpin`, the PyInstaller build and the binary's `--check`. A CI round trip takes about 10 minutes, so it is not a test loop. A merge into `main` releases nothing, but every run of the Release workflow with **Publish** ticked publishes a release (a pre-release from a branch); to check a branch's builds without releasing, run it by hand with **Publish** unticked (the archives stay on the run's page). Check workflow edits with `actionlint` (`docker run --rm -v "$PWD":/repo -w /repo rhysd/actionlint:latest`).
- A release published from the draft whose build fails stays a draft, but its tag is already created. Delete the tag (`git push origin --delete vX.Y.Z`) before trying again: the `version` job skips versions whose tag exists, so a leftover tag moves the next release on to the following version.
- Don't commit unless asked.
- **Label every pull request for the release drafter.** `.github/release-drafter.yml` reads the labels of merged PRs to write the draft release's notes and pick its next `vX.Y.Z` tag, so set one of these when opening a PR (`gh pr create --label <name>`):
  - `enhancement`: a new or changed user-visible feature. Raises the **minor** version.
  - `major`: a breaking change (a changed settings, output or file format, a removed feature or option). Raises the **major** version, and wins over every other label. It sets only the version, so add it on top of `enhancement` or `bug`.
  - `bug`: a fix. A **patch** release, which is also the default for any PR without a label that raises the version.
  - `documentation`, `dependencies`: listed under their own headings in the notes; **patch**.
  - `skip-changelog`: leaves the PR out of the notes and ignores it when picking the version (internal refactors, CI-only changes).
  The PR title becomes the release-note line, so write it as a short user-facing sentence. Merging releases nothing: the release drafter rewrites the draft after every merge into `main`, and the next hand-started Release run publishes the version it proposes (installed copies are offered it), so set the label before merging and never edit the draft by hand to fix a title or label.
- **UI changes need screenshots in the PR description**: every new or changed behavior and state (each button, menu, dialog and message, enabled/disabled/busy, success and failure, demo and camera variants where they differ), with a one-line caption each. Capture them from the real widgets without a display or camera: run `--demo` code with `QT_QPA_PLATFORM=offscreen` and save `widget.grab()` to PNG, patching `exec()` on dialogs and message boxes to grab instead of block, and mocking network calls. Don't commit the images to the feature branch: push them to the `pr-screenshots` branch under `pr-<number>/` and embed them with `https://github.com/<owner>/<repo>/blob/pr-screenshots/pr-<number>/<name>.png?raw=true`, which renders for anyone. Retake them when a later push changes the UI.
