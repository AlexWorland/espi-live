# AGENTS.md

Guidance for AI coding agents and developers working in this repository. See `README.md` for usage and the full layout.

## Overview

A live viewer for a FLIR Blackfly (BFS-U3-63S4M-C) Mono8 camera used for ESPI measurements, written in Python with PySpin/Spinnaker, OpenCV, NumPy and PySide6 (Qt). It must stay cross-platform (Windows camera PC, macOS and Linux). The camera runtime is a Windows PC (Python 3.10 with PySpin, SDK 4.2); the macOS checkout is for editing and camera-free `--demo` runs.

## Commands

```sh
./run.sh --demo                                    # Qt UI, synthetic video, no camera or PySpin
./run.sh                                           # try a real camera; offers demo mode if none found
PYTHONPATH=src python -m espi_live --check         # import everything (Qt, engine, PySpin if present), no window
PYTHONPATH=src python -m unittest discover -s tests   # camera-free tests
PYTHONPATH=src QT_QPA_PLATFORM=offscreen python -m coverage run -m unittest discover -s tests && python -m coverage report   # must stay at 100% (.coveragerc)
python -m py_compile src/espi_live/*.py            # required check after edits (no display or camera needed)
```

- `.venv` (Python 3.14) holds numpy, opencv-python and PySide6 from `requirements.txt`. PySpin is imported lazily by `camera.load_pyspin()`.
- PySide6 is required: there is no other front end (the legacy Tk UI was removed). Without it the program exits with a message.
- Windows camera PC: `scripts/windows/SETUP AND START ESPI.bat` validates and installs dependencies (including PySide6), then launches the app with `PYTHONPATH=src`.
- Do not run camera-acquisition code without the user's direction; the camera may be absent or in use. `--demo` and `--check` never open a camera.
- Outputs go to `<project>/output/{logs,frames,recordings}/` (`paths.OUTPUT_DIR`, independent of the working directory; next to the executable in PyInstaller builds); demo files are prefixed `dummy_`.

## Architecture (`src/espi_live/`)

| Module | Role |
|--------|------|
| `paths.py` | `PROJECT_ROOT`/`OUTPUT_DIR` (frozen-build aware), `timestamp()`, `output_folder()` |
| `processing.py` | `ESPIProcessor` (difference, averaging), `normalize_min_max`, `apply_palette` (the one definition of display color), `palette_rgb_table` (same colors as a GPU table), `DemoSource`, `watermark_demo` |
| `camera.py` | PySpin node helpers (`set_enum`/`set_bool`/`set_float`/`try_setting`, `read_string`/`read_int`), `read_identity`, `configure_camera`, `CameraSession(log, serial)` (open/grab/set_float/limits/read_values/close; `identity` and `info` after open), `list_cameras` → `CameraInfo`, `acquire_system`/`release_system` (shared, reference-counted PySpin System) |
| `camera_models.py` | Model detection without PySpin: `CameraIdentity` (reported vendor/model/serial/sensor/size; `short_name`, `description`, `warnings`), `parse_part_number` (Teledyne part-number scheme), `KNOWN_MODELS` (researched sensor and shutter; see `docs/camera/supported-models.md`) |
| `recording.py` | `AVIRecorder` (own thread, constant-rate timeline), `recording_path`, `save_frame` (PNG + title/notes sidecar) |
| `logs.py` | `AppLog`: per-run log file and stdout/stderr mirroring (`MirrorStream`) into a queue the UI drains |
| `engine.py` | `Engine`: worker thread that owns the source, processing, recording and saving; `Settings`, `FramePacket` |
| `channels.py` | `Channel`: one camera (or synthetic source) with its own `Engine`, saved `Settings`, limits and frozen display frame (`frozen`, `frozen_at`; dropped by `stop`); processing on/off (`start`/`stop`); `open_camera_channels`/`demo_channels` for startup; `PrefixedLog` |
| `qt_app.py` | Default front end: `MainWindow` (dockable controls/log, status bar), `GLImageView` (GPU), `CpuImageView` (fallback) |
| `updater.py` | Self-update of frozen builds from the newest full release (`/releases/latest`, which skips pre-releases): `check_for_update`, `download_update` (SHA-256 verified), `install_update` (Windows/Linux: moves the new build's `_internal-<build>` folder in beside the running one, then swaps the executable, keeping it as `*.old`; macOS: swaps the `.app`), `cleanup_previous_update` (staging folders, `*.old`, then, once that is gone, other builds' `_internal-*` folders, plus old single-file copies in the two folders above the program folder: `single_file_copies`, recognized by `is_single_file_copy` from their PyInstaller archive), `StartupCleanup` (`qt_app.run` starts it after the log, reporting removals there; it retries on a daemon thread while the previous build is still closing and is stopped before `finish_update` installs anything), `relaunch`, `UpdateWorker` (background thread the UI polls). Reads `_build_info.py`, which CI generates (build number, commit, repo, asset name, read-only token); never commit it |
| `feedback.py` | Feature requests to GitHub issues: `FeatureRequest`, `issue_payload` (labels `feature-request` and optional `enrich`), `submit` (POST with the Issues-only `FEEDBACK_TOKEN`), `browser_url` (prefilled page when there is no token), `FeedbackWorker` (background thread the UI polls) |
| `cli.py` | Argument parsing, front-end choice, `--check`, `--version`, `--update`, `--no-update-check` |

**Engine threading.** The front end chooses the source on its own thread before `start()` (`open_camera()` or `use_demo()`, so it can ask about demo mode), or calls `open_on_start(after=old_engine)` so the worker opens the camera itself (used when a camera is turned on while the window runs); after that, every PySpin call (grab, node writes, readback, close, live switch) happens on the engine's worker thread. A `CameraSession` must only ever be used by one thread at a time. The UI talks to the engine only through `update_settings(**fields)`, `request(action, **payload)` (`save`, optionally with a frozen display's `packet` and `frozen_at`; `reference`, `reset_previous`, `reset_average`, `switch_live`), `latest_packet()`, `status()` and the `events` queue (`camera_identity`, `camera_limits`, `record_off`, `switched_live` (payload: every detected `CameraInfo`), `switch_failed`, `open_failed`, `fatal`, `stopped`). Never touch Qt objects from the worker.

**Several cameras.** Each camera is a `Channel` with its own `Engine` and worker thread, so settings, reference, averaging and recording are per camera. The Qt `MainWindow` owns the list, displays `self.current` (its `engine` and `camera_identity` properties are the displayed channel's, which every control uses) and keeps the displayed channel processing. Sessions share the PySpin `System` through `acquire_system()`/`release_system()`, because `System.ReleaseInstance()` fails while any camera is still referenced; never call `GetInstance`/`ReleaseInstance` directly in package code. An error in one channel stops only that channel; the window closes when none is left.

**Frame flow.** Each worker iteration: grab (`CameraSession.grab(100)` or `DemoSource.next_frame` on a fixed schedule) → apply changed camera settings (rate-limited to 0.1 s; readback every 1 s) → Raw passes the frame through; Previous/Reference run `difference` → `average` (block) or `rolling_average` → `smooth_speckle` → optional `stretch_contrast` (min/max or percentile clip) → optional invert → (CLAHE path: gamma + CLAHE on the CPU) → demo watermark → publish an immutable `FramePacket` (newest wins; older ones are dropped) → feed the recorder → handle queued actions. A mode change resets averaging; `average` returns `None` until N frames accumulate (`rolling_average` returns every frame). Reference auto-refresh recaptures the baseline every `ref_refresh_s`.

**Display.** A `FramePacket` holds the Mono8 image plus the palette and gamma still to apply. `GLImageView` uploads it as an R8 texture (with mipmaps) and a fragment shader maps it through a 256-entry RGB table from `palette_rgb_table`; scaling, zoom and pan are GPU work. Saving and recording call `FramePacket.render()` → `apply_palette`, so files match the screen exactly (a test enforces this). `CpuImageView` is used when an OpenGL 3.3 core context is unavailable (for example some remote-desktop sessions). **Freeze** (`MainWindow.set_frozen`, Space) is display-only: the window holds the packet it last drew on the displayed `Channel` and stops drawing new ones, while the engine keeps acquiring, processing and recording; Save sends the held packet, and the amber banner over the image, status badge and button mark it. A frozen demo frame is dropped on `switched_live`, so it can never outlast the dummy-mode indicators.

**Demo mode.** `DemoSource` simulates exposure/gain via brightness; `watermark_demo` stamps "DUMMY MODE ACTIVE" into every published frame, so it appears on screen, in saved frames and in recordings, and the Qt UI also shows a red banner, title and status badge. Demo data must never be mistakable for camera data. The "Switch to live capture" retry must leave the synthetic stream running on failure, and on success reset measurement state and stop any demo recording.

## Rules

- Before changing PySpin, camera lifecycle, node-map or image-buffer code, read `docs/camera/README.md` and the files it points to: `spinnaker-pyspin.md` always, `blackfly-bfs-u3-63s4m-c.md` for model-specific settings, `acquisition-and-performance.md` for streaming, ROI, pixel format, frame rate, preview latency, recording or triggering.
- Verify a node is readable/writable before writing it and clamp numeric values to device limits (`set_enum`/`set_bool`/`set_float` wrapped by `try_setting` do this). Release every `GetNextImage` result in a `finally` (`CameraSession.grab` does), and `.copy()` `GetNDArray()` data that outlives the image. Preserve safe lifecycle handling on errors.
- Don't change default exposure (8000 µs), gain (0 dB), frame rate (30 fps) or recording behavior without calling out the impact. Don't assume the displayed rate equals the camera's acquisition rate.
- Keep processing, camera and recording code free of GUI imports so the front end and the tests share it. Keep display color defined only in `processing.apply_palette`.
- Keep it cross-platform: no platform-only GUI SDKs; guard OS-specific calls (as `WindowsPreviewTimer` does). The GPU path needs only OpenGL 3.3 core through Qt; keep the CPU fallback working.
- Don't reintroduce OpenCV HighGUI windows: mixing them with another toolkit caused fatal Windows crashes.
- Every function needs a docstring in the existing `Args: ... / Returns: ...` format.
- Put tentative work in `experiments/`; promote it into `src/espi_live/` only when it becomes the intended maintained implementation. Use descriptive, purpose-based filenames; date-based names belong in `archive/`.
- Store recordings under `output/recordings/` and still frames under `output/frames/`. Don't commit generated media.
- Keep Windows and Bash helpers in `scripts/` and update their paths whenever a referenced file moves (they resolve `third_party/` and `src/` relative to the repo root).
- Updates must never start the new build while the camera is open: the Qt front end installs and relaunches only after the engine has stopped (`qt_app.finish_update`). Keep the release archive names, `build-info.json` and `_build_info.py` fields in `build-binaries.yml` in step with `updater.py` and `feedback.py`, and the Windows/Linux program folder too: PyInstaller onedir with `--contents-directory _internal-<build>` (`updater.CONTENTS_PREFIX`), holding only the executable and that folder (the smoke test checks it; the updater refuses anything else). A running Windows program's executable and loaded DLLs can be renamed but not overwritten or deleted, so never give two builds the same library folder name, and never make the updater touch the running build's folder. Startup cleanup deletes only update leftovers, other builds' library folders and files it has verified as single-file builds of this program; never `output/` or token files. `build-info.json` lists the archives' SHA-256 under `archives`; never put a folder archive under `sha256`, the key the single-file builds (build 6 and earlier) read, whose updater would put the folder where their executable was. A public release must always carry `build-info.json` (the updater reads `/releases/latest`), which is why published drafts are held as drafts until the archives are attached; the updater orders builds by the `build` number in that file, never by tag name.
- Tokens baked into builds are extractable by anyone with a binary, and the binaries are public: keep each to the minimum scope (`UPDATE_TOKEN`, optional now that the repository is public, Contents: read; `FEEDBACK_TOKEN` Issues: read & write) and never bake in AI or write-to-code credentials. Copilot runs only in Actions (`COPILOT_PAT`). In workflows, pass issue text through `env:`, never `${{ }}` inside `run:`.
- Don't add a virtual-environment or dependency-management system (pyproject, lockfiles) unless asked.
- Keep `README.md` accurate when layout, entry points or setup change, and add a `CHANGELOG.md` entry for user-visible changes.
- After edits, run `python -m py_compile` on the changed files and the tests. Keep line coverage at 100% (`coverage report` fails below it, and so does the release workflow): add tests with new code, and don't use `# pragma: no cover`. Tests must never open a camera, touch the network, write to the real `output/` folder or block on a dialog.

## Git

- This repository is public (GPL-3.0, `LICENSE`). Never commit the FLIR SDK, other people's scripts or personal documents to it: once pushed, they stay reachable through pull-request refs even after a history rewrite. SDK files go in the private `espi-live-sdk` repository (Git LFS there).
- Work in a clone of this repository. Clones of the private `espi-live-archive` (the history before the repository went public) still hold the SDK in their history: never push their branches here or add this repository as their remote. Before pushing, `git log --oneline origin/main..HEAD` must list only your own commits. This repository has no Git LFS files, so if a push starts uploading LFS objects, stop it at once.
- `.gitignore` excludes `.venv/`, `__pycache__/`, `.DS_Store`, `.omc/`, `output/`, `build/`, `dist/`, `research/` (never push it), `third_party/`, Office lock files, and large binaries (`*.avi`, `*.zip`, `*.whl`, `*.dmg`, `*.tar.gz`, `*.pptx`). Don't force-add them.
- CI checks out `espi-live-sdk` into `third_party/`, fetches only the LFS files each platform needs (`git lfs pull --include`) and caches them, since LFS bandwidth is metered; `setup-python` caches pip downloads (`cache: pip`). Keep that behavior when editing `build-binaries.yml`.
- The Linux build installs FLIR's Spinnaker 4.4 `.deb` packages, whose install scripts expect an interactive desktop. Keep these workarounds in `build-binaries.yml`: the `debconf-set-selections` preseed of `libspinnaker/accepted-flir-eula` (without it libgentl's preinst exits 2 because it cannot show the EULA); `sudo env -u SUDO_USER` for that `apt-get install` (the preinst asks the sudo user for analytics consent under `set -e`, which exits 30 without a terminal and cannot be preseeded because the script resets the answer; with no user found it skips the question, and libspinnaker's postinst skips its analytics ping); `spinupdate` (`_PySpin` links against `libSpinUpdate`); and `libavcodec60 libavformat60 libavutil58 libswscale7` (FFmpeg, which `libSpinVideo` links against but does not declare).
- Check Linux build changes locally before pushing them: run the job's commands in an `ubuntu:24.04` container (`docker run --platform linux/amd64`) as a non-root user calling `sudo`, through `ldd` on `/opt/spinnaker/lib/*` and `_PySpin` (no `not found`), `import PySpin`, the PyInstaller build and the binary's `--check`. A CI round trip takes about 10 minutes, so it is not a test loop. Every merge into `main` publishes a release, and so does every run of the Release workflow with **Publish** ticked (a pre-release from a branch); to check a branch's builds without releasing, run it by hand with **Publish** unticked (the archives stay on the run's page). Check workflow edits with `actionlint` (`docker run --rm -v "$PWD":/repo -w /repo rhysd/actionlint:latest`).
- A release published from the draft whose build fails stays a draft, but its tag is already created. Delete the tag (`git push origin --delete vX.Y.Z`) before trying again: the `version` job skips versions whose tag exists, so a leftover tag moves the next release on to the following version.
- Don't commit unless asked.
- **Label every pull request for the release drafter.** `.github/release-drafter.yml` reads the labels of merged PRs to write the draft release's notes and pick its next `vX.Y.Z` tag, so set one of these when opening a PR (`gh pr create --label <name>`):
  - `enhancement`: a new or changed user-visible feature. Raises the **minor** version.
  - `major`: a breaking change (a changed settings, output or file format, a removed feature or option). Raises the **major** version, and wins over every other label. It sets only the version, so add it on top of `enhancement` or `bug`.
  - `bug`: a fix. A **patch** release, which is also the default for any PR without a label that raises the version.
  - `documentation`, `dependencies`: listed under their own headings in the notes; **patch**.
  - `skip-changelog`: leaves the PR out of the notes and ignores it when picking the version (internal refactors, CI-only changes).
  The PR title becomes the release-note line, so write it as a short user-facing sentence. Merging releases at once: the Release workflow rewrites the draft after every merge into `main` and publishes the version it proposes, and installed copies are offered it, so set the label before merging and never edit the draft by hand to fix a title or label.
- **UI changes need screenshots in the PR description**: every new or changed behavior and state (each button, menu, dialog and message, enabled/disabled/busy, success and failure, demo and camera variants where they differ), with a one-line caption each. Capture them from the real widgets without a display or camera: run `--demo` code with `QT_QPA_PLATFORM=offscreen` and save `widget.grab()` to PNG, patching `exec()` on dialogs and message boxes to grab instead of block, and mocking network calls. Don't commit the images to the feature branch: push them to the `pr-screenshots` branch under `pr-<number>/` and embed them with `https://github.com/<owner>/<repo>/blob/pr-screenshots/pr-<number>/<name>.png?raw=true`, which renders for anyone. Retake them when a later push changes the UI.
