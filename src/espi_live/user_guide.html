ESPI live — User Guide

ESPI live shows a live image from a FLIR Blackfly BFS-U3-63S4M-C Mono8 camera (or an analog camera through a capture adapter) and turns it into ESPI (electronic speckle pattern interferometry) measurements by subtracting frames. This guide explains every control and walks through the operations you will use most.

Offline guide Open from Help → User Guide (F1) Links work in this page

Quick start #

  1. Start the app with a camera connected (or choose demo mode when asked).
  2. Stay in Raw view and position and focus the specimen.
  3. Adjust Exposure so the image is bright but not washed out. Use Gain only when exposure is not enough.
  4. Switch to Reference and press F (or Set reference) with the specimen in its resting state. Detailed steps.
  5. Load or deform the specimen. The difference image shows the ESPI fringe pattern.
  6. If the pattern is noisy, raise Average N. If it is faint, raise Difference gain (Fixed gain) or switch Scaling to Auto stretch.
  7. Press S (Save frame) to keep a still, or Record AVI to capture a sequence. Add a title and notes before saving to identify the measurement.

Starting the application #

With a camera #

On the Windows camera PC, double-click scripts/windows/SETUP AND START ESPI.bat. It checks Python, OpenCV, NumPy, PySide6, PySpin and the Spinnaker SDK, asks before installing anything, and launches the app when validation passes. After an install, close any installers and run the same file again.

On macOS or Linux, from a terminal in the project folder:

./run.sh

On Windows, from the project folder in a command prompt:

set PYTHONPATH=src
python -m espi_live

The app opens the first FLIR camera it finds. If no camera is detected, it offers to start demo mode; choose No to quit instead.

Without a camera (demo mode) #

./run.sh --demo

Demo mode shows a simulated ESPI signal: what an ideal camera would record looking at a speckle interferometer whose specimen is a drumhead (an ideal circular membrane clamped at its rim; no material model). The sensor is an ideal sensor: brightness is proportional to exposure and gain, frames are rounded to 8 bits and clip at 255, and there is no shot, read or fixed-pattern noise. Every processing step (Previous, Reference, averaging, gain or stretch, the LabVIEW flow, the noise floor) therefore works on a signal whose correct result is known, so you can check the processing by eye, learn the controls, and test saving and recording without a camera.

The Simulated object control (Camera section, demo cameras only) chooses what the drumhead does; the note under it says what is driving it:

  • Still — nothing moves. Previous view is exactly black and Measure noise floor reads 0.
  • Slow deformation (the default) — a pad at a third of the radius presses the drum in to 8 fringes over 5 s, holds 1 s, releases over 5 s and rests 1 s, every 12 s. Against a reference, closed rings grow around the pad and crowd toward it (a membrane's dent is logarithmic); outside the rim stays black.
  • Vibration — drum mode (1, 1) at 1000 Hz, peak 16 rad (5 J0 fringes). Set the reference on Still first, then choose Vibration: two lobes of 1 − J0 bands either side of a dark nodal diameter. At 8000 µs (8 whole cycles per exposure) Previous view stays black; at 8700 µs the exposure starts at a different phase each frame and the pattern flickers, as on a real camera.
  • Follow DAQ — the NI DAQ window's frequency generator drives the drum (Devices → NI DAQ…; the Simulated device works). 0.1 V at the fundamental gives 16 rad. Its resonances: 628 Hz (0, 1) rings, 1000 Hz (1, 1) one nodal diameter, 1340 Hz (2, 1) a nodal cross, 1441 Hz (0, 2) a nodal circle, 1665 Hz (3, 1) six lobes, 1831 Hz (1, 2); higher modes need more volts. A counter's square wave counts as its fundamental. The piezo's sine (locked to the generator) modulates the reference beam and moves the zero-order fringe.

In every case the DAQ piezo moves the simulated reference mirror: 1500 nm per DAQ volt (a 100 nm/V stack behind a gain-15 amplifier), so the default 0.05 V step shifts the reference phase by about 85°. The exposure average is exact for any number of drive cycles per exposure, and frames follow an ideal sensor clock at the requested frame rate.

Reference piezo (triangle, decorrelation) (a checkbox under the note; off by default) ramps the simulated reference mirror with a slow triangle wave, 1 Hz and 1.2 µm peak to peak, as a piezo on the reference beam does on the bench. The reference phase then changes between frames (about 90° at 30 fps), so the speckle decorrelates: in Previous view a still area shows bright speckle, and a vibration shows |J0| fringes with a white nodal line where the drum does not move (without it, a steady vibration's Previous view is black). A rolling Average N smooths the speckle into clean fringes. It works with every object and adds to the DAQ piezo.

Demo data is clearly marked. A red DUMMY MODE banner (in the Controls panel) and a status badge are visible, and every saved frame and recording carries a DUMMY MODE ACTIVE watermark and a dummy_ filename prefix. Demo data is never presented as camera data.

Demo frames are 960×640. The watermark covers the top ~10% (at least 42 px), so that band is hidden in demo previews, saved frames and recordings.

Command line #

There is one Qt front end. Useful options:

  • --demo — synthetic video without touching a camera; --demo-cameras N creates several synthetic cameras.
  • --check — load every module without opening a window and exit. --version prints the build number.
  • --update — install the newest full release without opening a window. --no-update-check skips the startup update check and the source download.
  • --send-changes — send changes made in the downloaded source folder (see Updates, features and Codex).

Controls reference #

Each Controls section can be collapsed: click its heading to hide or show it. The choice is remembered between runs.

Demo banner and Switch to live capture #

These appear only in demo mode.

  • DUMMY MODE banner and badge: a reminder that the image is synthetic.
  • Switch to live capture: retries camera detection without restarting the app. If a camera is found, the app resets to Raw view, clears measurement baselines, stops any demo recording, and continues with live frames. If no camera is found, a warning explains why and demo mode keeps running.

Toolbar #

  • Simple UI — on, only the basic controls are shown (views, Record AVI, Save frame, Set reference, Compare, Pixels, the camera, Exposure and Gain); off, every control, section and toolbar button is shown. Switching changes only what is displayed: settings and the camera are untouched, and the choice is remembered for the next run.
  • View modes — Raw, Previous and Reference; see View.
  • Raw difference — show only the difference between two raw camera frames: each pixel is |live − previous| in the camera's own grey levels. While it is on (the button turns red and the view buttons grey out) every other step is bypassed: noise reduction, single field, filters, averaging, difference gain, stretch, gamma, flip and display tone. Your settings are kept and come back when you turn it off; the camera's own exposure and gain are unchanged. Recordings are named espi_rawdiff_*.avi, and the comparison window shows the two raw frames.
  • Record AVI — start or stop recording the displayed image. The recording label shows the output rate.
  • Freeze (Space) — hold the displayed image without saving it. The camera keeps acquiring, averaging, reference refresh and recording continue. An amber FROZEN bar over the image and a status badge mark the held frame; press Space again to return to live. Save frame saves the held image, and Set reference still uses the live camera frame.
  • Save frame (S), Set reference (F), Pixels (P) (see Read pixel values), Reset last (R), Reset average (A) — the same actions as the measurement and capture sections.
  • Zoom — drag, click or use the arrow keys on the slider to zoom from fit (100%) up to 64×; Fit (0) and 1:1 (1) jump to those levels. The mouse wheel zooms around the cursor and dragging pans.

Every control, menu item and status readout has a hover tooltip that explains it. Tip text waits briefly so it does not flicker as the pointer moves.

View #

Choose how each frame is built. The modes use the same camera frames; with Average N = 1 Raw, Previous and Reference update at the same rate. With N > 1 (4 by default), Previous and Reference publish a new image only after N frames. The Phase button appears once the NI DAQ's piezo driver is assigned; see Phase view.

Raw

The direct Mono8 camera image with no subtraction or stretch; the gamma slider still applies. Use it for positioning, focusing and checking exposure.

Previous

The absolute difference between this frame and the previous one. Stationary areas are black; anything that changed since the last frame is bright. The first frame after switching becomes the baseline and displays black.

Reference

The absolute difference between this frame and a stored reference frame. Capture the resting state once, then watch how the specimen changes against it. With nothing stored, Reference view averages the next Ref. frames frames into one by itself (16 by default); F takes a new one.

Phase

Phase-shifting ESPI: the piezo steps the reference beam between frames and each pixel's phase change since the phase reference is shown, with its sign: mid-grey is no change, black to white one fringe (2π). Needs the NI DAQ's piezo driver; the view starts by itself once the piezo has been applied in the DAQ window.

Changing the view mode clears any partial average. Switching to Previous starts a fresh baseline on the next frame. The reference frame is kept until you capture a new one, switch to live capture successfully, or close the app.

Below the view buttons, a hint line describes the current mode and reminds you when a reference is still needed.

Camera #

  • Exposure (microseconds) — how long each frame collects light. It changes brightness and motion blur. The default is 8000 µs. Longer exposure means a brighter image but limits the maximum frame rate.
  • Gain (dB) — electronic amplification. It brightens the image but also amplifies noise, so prefer more exposure when the specimen allows it. The default is 0 dB.
  • Requested FPS — the frame rate you ask the camera for. The default is 30 fps. The camera may deliver less if exposure, USB bandwidth or the camera's own limits prevent it.
  • Simulated object — demo cameras only: what the simulated drumhead does (Still, Slow deformation, Vibration or Follow DAQ; see demo mode). Saved with that demo camera's settings. Reference piezo under it adds the reference-beam triangle wave for decorrelation.
  • Noise reduction — blends each camera frame with the previous ones (0 = off, 95 = strongest; each step adds the same amount of memory, so 10 keeps about three frames and 95 about twenty) to remove random sensor noise in every view, Raw included, while keeping the speckle ESPI fringes depend on. Higher values smooth more but leave a trail behind motion and weaken Previous-view fringes; a Reference captured with it on is less noisy too.
  • Single field (interlaced camera) — shown for an interlaced analog source; off by default (full frames, as the LabVIEW program used). On, it keeps one field, doubled to full height, removing the 1/60 s offset between fields at the cost of half the vertical detail.
  • Presets — your saved presets, with Apply, Save as… and Delete, and Reset camera to defaults…. See Camera profiles and presets.

Each control has a slider for quick changes and a number box for exact entry: drag the slider, type a value and press Enter, or use the arrow keys.

When a camera is connected the sliders adapt to its readable limits, but this build clips them to 0–50,000 µs exposure, 0–30 dB gain and 0–60 fps. The camera itself can reach 30 s and 47.99 dB, but those values are not exposed in the UI. Out-of-range values are clamped. The 100 ms frame-grab timeout also means very long exposures can stop the stream from keeping up.

Each time the app opens the camera it writes Mono8, continuous acquisition, auto-exposure and auto-gain off, and the exposure, gain and frame rate shown in the controls, and selects NewestOnly buffering. Settings made in SpinView are replaced; set exposure, gain and frame rate in the app.

Rate limiting and the readout

Changes are sent to the camera at most about ten times per second, so dragging a slider stays smooth. The readout underneath the controls is refreshed once per second and shows:

Applied: 8000 µs, 0.0 dB; FPS set 30.0, resulting 29.8
  • Applied is what the camera actually accepted, which can differ from what you requested if the camera clamped a value.
  • FPS set is your request; resulting is the measured acquisition rate. A lower resulting rate is normal at long exposures or high resolution.

In demo mode this readout says that exposure, gain and FPS are simulated.

See Adjust exposure, gain and frame rate for practical steps.

ESPI measurement #

These controls apply to Previous and Reference views. Raw ignores them.

Start with Live preview while aligning: Previous view, averaging off, noise reduction 0, speckle filter off and Gray display. For a still-object measurement, Measurement selects Reference view, an 8-frame block average, Median at 3 px, reference refresh 2 s and stretch clip 0.5%. Press F when the object is still. For a vibrating object through the analog camera, Peak hold selects Previous view, a noise threshold of 6 levels, Median at 3 px, a 1 s peak hold window, a 1 s steady range, stretch clip 0.5% and S-curve contrast 30%: each pixel keeps its largest change over the last second, so a driven drum's ring pattern builds up. It keeps your sensitivity floor; press Calibrate noise with the drive off to measure it. No preset changes exposure, gain, frame rate or recording, and each turns off the fringe-enhancement and display controls it does not use.

The default noise pipeline. Every camera, the analog one included, starts with Average camera frames, then subtract on and Average N 4 (camera and capture noise fall by half before the difference), a 16-frame reference that Reference view captures by itself, and the Oriented speckle filter at 11 px. A camera with a saved profile keeps what it was left with; Reset camera to defaults… brings the pipeline in. For the full frame rate, set Average N to 1.

LabVIEW flow, the toggle under them, switches the displayed camera to the processing of the LabVIEW ESPI 1.5 program with that program's saved defaults, the known-good flow for the Sony XC-ST50. It is off by default (it used to be on for that camera). It sets Reference view and captures a one-frame reference at once (and whenever Reference has none), full frames, Fixed gain 42× applied to each frame before averaging, and turns off camera-frame averaging, the averaged reference, noise reduction, the noise threshold, beam-brightness correction, the speckle and outlier filters, peak hold, local normalization, stretch, the display brightness, gain and contrast, and invert. If you turn averaging on, it sums N + 1 frames and divides by N, as the program did. Exposure, gain, frame rate, recording and the flip keep their values. Turn it off to get your own settings back; changes made while it is on are dropped. Each camera keeps its own state.

Help → Which settings should I use? explains the presets and can apply them to the displayed camera. Reference refresh also hides motion slower than its interval; use 0 for a fixed before/after.

Processing order: noise reduction → (frame average) → difference (N frames back) → noise threshold → beam brightness → outlier filter → average → speckle filter → noise floor → peak hold → fixed gain, stretch or local normalization → invert → brightness, gain and contrast → gamma. Phase view: piezo phase steps → wrapped phase → minus the reference phase → sine/cosine filter. The frame average and the noise floor run only when their checkboxes are on. With Gain before averaging, the fixed gain moves to just before the outlier filter. Raw skips difference processing and still applies noise reduction, display gamma and the display brightness, gain and contrast.

  • Average N (default 4) — with Average camera frames on (the default) N camera frames are averaged before each difference; with it off, each displayed image becomes the mean of N consecutive difference frames. Averaging reduces random noise at the cost of a slower displayed update: at 30 fps and N = 5, a new averaged image appears about six times per second. While the first N frames are collected the image stays unchanged, and changing N or the view mode restarts the count. Recording follows the averaged rate.
  • Rolling average (updates every frame) — a running average that still updates at the camera rate. Use it when you want to watch fringes move instead of waiting for each block of N frames.
  • Average camera frames, then subtract — Average N averages the camera frames themselves, one image per N frames, and the averages are subtracted. Each difference is an absolute value, so averaging differences never brings camera noise to zero: it settles into a grey floor. Averaging the frames first cuts the noise by the square root of N and keeps a steady change such as time-averaged fringes. Rolling average does not apply; in Previous view Frames back counts averages; in Reference view, set Ref. frames to N or more so the reference is as quiet. On by default, with Average N 4 and 16 reference frames. In the Phase view each phase step averages N frames.
  • Ref. frames — how many camera frames F (and the automatic reference) averages into the reference (1–60, default 16; 1 is one frame). A one-frame reference keeps that frame's sensor noise, and the noise then shows in every Reference difference as a fixed grain that Average N cannot remove; averaging 8–30 frames of a still object quiets it, which matters most for a noisy or analog camera. The frames are taken at the same point as before (after single field and noise reduction). While they are collected the status bar counts them (Capturing reference: 7/30 frames) and the old reference stays in use until the new one is complete. A new view keeps the capture going; changing Single field or Noise reduction cancels it, so frames of two kinds are never mixed.
  • Ref. refresh — Reference view recaptures the reference every N seconds so slow drift (air currents, heat) cancels; 0 keeps one reference until you press F. Each refresh averages Ref. frames frames, and the time counts from the start of the last capture. When averaging takes longer than the refresh (30 frames at 30 fps is 1 s), references are captured back to back and the log says so.
  • Frames back — which earlier frame Previous view compares with: 1 is the frame just before. A larger number spans more time, so slow changes show instead of cancelling (the LabVIEW program did this by waiting between grabs). Each step keeps one more frame in memory. 1–30.

Fringe enhancement #

  • Outlier filter — on every difference frame, before averaging, a pixel further from its neighbourhood's mean than the neighbourhood's spread (standard deviation) becomes that mean. Isolated hot or dark pixels go; fringes and smooth areas stay. This is NI Vision's Lowpass filter from the LabVIEW program. Width in pixels, 0 = off; try 3 px.
  • Speckle filter — Oriented (the default), Gaussian, or edge-keeping Median (capped at 5 px to keep the frame rate). Oriented measures which way the fringes run and smooths along them, not across, so dense fringes survive a width that would blur them away with Gaussian; where no direction stands out it acts like a Gaussian. It takes about 45 ms on a 6 MP frame.
  • Filter width — blur in pixels that removes pixel-scale speckle; keep it below the fringe spacing. 0 = off. 11 px by default; lower it if dense fringes fade.
  • Scaling — how difference values become brightness. Fixed gain multiplies every difference by Difference gain and shows anything above 255 as white, as the LabVIEW program did: a still scene's few levels of noise stay dark and the brightness does not pump. Auto stretch maps each difference frame's darkest and brightest pixels (after Stretch clip) to 0 and 255, so fringes fill the display; a constant difference image maps to black. The Sony XC-ST50 starts in Fixed gain, the Blackfly and demo mode in Auto stretch. The status bar shows the input and scaled ranges, before gamma.
  • Difference gain — Fixed gain's multiplier, 1–64×; 42× by default, the LabVIEW program's Constant, so any difference of 7 grey levels or more is white. Lower it when noise shows as grey grain.
  • Gain before averaging (LabVIEW order) — Fixed gain only. On: the gain is applied to each frame (saturating at 255) and Average N averages those frames, then multiplies the mean by Average multiplier, the LabVIEW program's averaging maths. Off: the raw differences are averaged and the gain is applied once.
  • Average multiplier — scales the average in LabVIEW order (with Average N above 1); 1 to start.
  • Stretch clip — Auto stretch only. Lets this percentage of the darkest and brightest pixels saturate so a few stray speckles do not flatten the contrast; 0 = exact min/max, about 0.5% when a few speckles dominate.
  • Invert — swaps bright and dark fringes.
  • Sensitivity floor — with Auto stretch or Local normalization, white is never fewer than this many grey levels of difference, so a still scene's camera noise stays dark while real fringes use the full range. Video-capture devices start at 30; 0 = off.
  • Calibrate noise (object still) — in Previous or Reference view, with the object at rest, measures the difference noise for 2 s and sets the Sensitivity floor to twice its peak. In Raw it logs a warning and does nothing.
  • Noise threshold — right after the subtraction, differences below this many grey levels become 0. Hides camera noise; too high also hides faint fringes. 0 = off; try 3–8.
  • Subtract noise floor — takes each pixel's measured still-scene level off every difference, after averaging and the speckle filter, so a still scene shows black instead of grey grain. The level is per pixel because noise grows with brightness. Unlike Noise threshold it keeps faint changes that last across the average, so use it with Average N 4 or more. Off by default.
  • Measure noise floor (object still) — in Previous or Reference view, with the object at rest, records each pixel's difference level (its mean plus one standard deviation) for at least 2 s and 16 images; the status bar counts the images. The map fits only the settings it was measured with: after changing the view, the reference, exposure, gain, averaging or the filters before it, the status bar asks for a new measurement and nothing is subtracted. Changing them while it runs cancels it. In Raw it logs a warning and does nothing.
  • Steady range — Auto stretch only: the range shrinks only over this many seconds, so the contrast stops pumping; a growing range is followed at once. 0 = every frame.
  • Even out beam brightness — divides each difference by the local illumination so the centre of the laser spot no longer dominates; unlit areas go black. Off by default: it can amplify noise at the beam's edge.
  • Peak hold window — each pixel shows its largest difference within the last N seconds (a sliding window). In Previous view a steady vibration then builds up on screen. 0 = off; try 3 s.
  • Local normalization — window in pixels: each pixel is compared with the mean and spread of the difference around it, in place of Fixed gain or Auto stretch, so faint and strong fringes get the same contrast. Mid-grey is the local average. Use a window wider than the fringe spacing. 0 = off; try 41–81 px.

Scaling, clip and invert apply to difference views; Raw is never scaled or inverted.

Display #

The display is always grayscale. Gamma applies in Raw, Previous and Reference views.

  • Gamma — a display curve from 0.1 to 3.0. Values below 1 darken midtones and values above 1 brighten them. Gamma does not change the measurement data, only how it is displayed and saved. 1.0 leaves the image unchanged.
  • Brightness, Gain and S-curve contrast — one lookup table applied in every view before gamma: Gain multiplies the displayed image (bright values saturate), the S-curve darkens values below mid-grey and brightens those above, and Brightness adds grey levels. Saved frames and recordings match the screen. All off by default (0, 1×, 0%).

See Get the best contrast.

Capture and saved frames #

  • Record AVI — when checked, writes the displayed image to an AVI file at a steady output rate. In Previous/Reference the output rate is the source rate divided by Average N, capped at 30 fps and floored at 1 fps. In Raw view Average N is ignored. Recording includes gamma, scaling and, in demo mode, the watermark, so the file matches the screen. The label beside the button shows the output rate, and recording continues while you move, resize or interact with the window.
    • If encoding cannot keep up, intermediate preview frames are skipped and the AVI timeline still advances; when acquisition is slower than the output rate, the last frame is repeated. The log reports skipped frames and late encoder intervals when the file is closed.
    • Changing the view mode, or Average N or Rolling average in Previous/Reference, closes the current AVI and starts a new one. Other changes do not split the file: gamma, Scaling, Difference gain, Stretch clip, Outlier filter, Speckle filter, Invert, Frames back, exposure, gain, FPS, noise reduction, Single field, Set reference, Reset last and Reset average all continue writing to the same file. Stop and restart the recording after any of them, or the file will mix processing configurations or measurement baselines.
    • Unchecking Record AVI finishes the file cleanly. Closing the app also finishes it, waiting up to about 5 seconds for the writer; the log prints the final path and frame count.
  • Title (optional) — a short label added to the saved PNG filename. Characters that are unsafe in filenames, including spaces, become underscores; leading/trailing underscores are removed and the result is limited to 80 characters.
  • Notes (optional) — free text stored in a sidecar .txt file next to the PNG. When the display is frozen, the sidecar also records when it was frozen.
  • Save frame (S) — saves exactly what is on screen as a PNG. If no display frame is ready yet, the log says No current display frame is ready to save. If a title or notes are present, a .txt file with the same base name records the title, notes and whether the source was the camera or demo mode.
  • Set reference (F) — stores the current live camera frame as the reference and resets averaging, or, with Ref. frames above 1, the average of the next that many frames. This is the same reference used by Reference view; when the display is frozen, Set reference still captures the live camera frame, not the frozen image. The log records the noise reduction it was taken at. If Noise reduction is changed afterwards, the log and the Reference view's hint say the reference was taken at another setting (Reference was taken at noise reduction 0; press F to retake); it is not retaken by itself.
  • Compare (C) — opens a window with three live images of the displayed camera side by side: the stored Reference, the Current frame (both as Raw view shows them: gamma only, flip applied) and the processed Difference. In Reference view the difference is exactly the main image, averaging included; in Raw view it is one difference from the reference with the same filters, without averaging. In Previous view the first panel becomes Previous (N frames back): the exact earlier frame that view subtracted (after single field and noise reduction, like the current frame), and the difference is again exactly the main image. With Average N above 1, the first average is waited for (the Difference panel says how many frames are in so far); after that all three update together each time an average completes. Changing the view while the window is open switches what it shows. Under each image a line says how the reference or previous frame was taken and how the difference was made. Use it to check that the reference is clean and was taken at the current settings. Without a reference (or earlier frame) the panels say so. Its Freeze holds the three images (the main window stays live), Save all three writes them as shown (PNG) with one notes file that carries the main window's title and notes (the files are named reference or previous, current and difference), and it has its own Set reference (F), which is greyed out in Previous view because that view takes its earlier frame by itself. It follows the displayed camera, and the images are only made while it is open (at most 10 a second), so a closed window costs the camera nothing.
  • Reset last (R) — forgets the stored previous frame. Previous view then starts a fresh baseline on the next frame (with Average N = 1 that is one black frame before differences resume; with N > 1 the first displayed image is an average that includes it). It does not affect the reference.
  • Reset average (A) — discards a partial average. The next displayed image restarts the N-frame count. Useful after a disturbance so one disturbance does not smear into the next measurement.

Before you record: in Reference view, confirm a reference exists and the image is not black; in Previous view, wait for the first baseline frame. A recording started before either exists contains black frames. Stop the recording before changing exposure, gain, FPS, gamma or scaling, or before Set reference, Reset last or Reset average. Check free disk space first: the AVI is full-resolution MJPG, there is no size limit or free-space check, and a full disk stops the recording.

Hover one for its name, or for what it is doing while it is greyed out. See Updates, features and Codex.

  • Recording state — off, or the AVI output rate while recording.

With Average N = 1, a lower displayed rate than processed rate means the display or window compositor is the bottleneck. With N > 1 (and Rolling average off), Displayed is expected to be about Processed/N because a new image is published only after N frames.

Log panel #

The log is the application's record of what happened. It is timestamped and scrolls automatically. It reports startup and streaming, camera timeouts and failures, view changes, every saved file and its path, recording start and finish with frame counts, averaging and reference actions, demo/live switches, and errors. Applied camera settings are shown in the camera readout beneath the controls, not in the log.

Each run writes output/logs/espi_<YYYYMMDD_HHMMSS_microseconds>.log. When reporting a problem, include the relevant lines from this panel or that file.

Each line includes a level and thread name. Help → Open log folder opens the logs directory. The newest 50 run logs are kept, along with active runs. Unexpected errors are reported as public GitHub issues after personal details are scrubbed. Help → Send error reports automatically controls delivery; --no-error-reports also disables it. Run logs are also sent to the developer, scrubbed the same way, so problems can be looked into without anyone having to send logs by hand; they go to a private repository, not a public page. In the same way, while a real camera is processing, the program sends a still image and, less often, a short video clip of each camera, both the raw camera frames and the processed view, to a private repository, so the developer can see what real setups look like. Demo mode never sends anything.

The log keeps the most recent 2000 lines in the window; the file keeps the full run. Lines from several cameras start with the camera's serial number.

If output/ is not writable (for example the app is in a protected folder), no log, frame or recording file can be written. The log panel and console remain, but move the app to a writable folder to capture files.

Several cameras #

A Cameras section sits at the top of the Controls panel. With one camera it holds only the Display list, which names that camera; the Process rows below appear when more than one camera is connected.

  • Display picks the camera shown in the window.
  • Each camera has a Process checkbox. A checked camera keeps acquiring, processing and recording while another camera is displayed. The displayed camera always processes, so its checkbox is locked on; choosing an unchecked camera in Display turns it on.
  • Each row shows that camera's processed rate and REC while it records.
  • Every camera has its own settings, reference, average, display options, freeze frame and Record state. Controls, the toolbar and shortcuts always act on the displayed camera.
  • Unchecking Process stops that camera (finishing its recording and releasing it) but keeps its settings for next time; its reference and running average start fresh. At startup only the first camera that opens is processed.
  • Log lines from each camera start with its serial number. An error in one camera turns only that camera off.

Several 6.3 MP cameras streaming at once can exceed one USB 3 controller's bandwidth. Watch each row's frame rate; lower the frame rate or use separate controllers if it drops. --demo --demo-cameras 3 simulates three cameras for trying this without hardware.

Camera profiles and presets #

Every camera has its own profile: exposure, gain, frame rate, the view, and every processing and display control, including whether the LabVIEW flow is on. A change made while one camera is displayed never reaches another camera. With several cameras, the Camera section starts with Settings of and the camera's name, so it is always clear whose settings you are editing; pick another camera under Display to edit its profile instead.

Saved between runs

  • Each camera's profile is saved about a second after you stop changing it, when you switch to another camera, and when the program closes. The next time that camera is connected it starts with the same values, and the log says so: BFS (12345678): saved settings restored (exposure 12000 µs, gain 2 dB, 30 fps, Reference view).
  • A FLIR camera is recognised by its serial number, and an analog capture stick by its USB ID and name (its video N number changes between runs). Demo cameras keep separate profiles, so demo values never land on a real camera, also not after Switch to live capture: the live camera starts with its own saved profile, or with its defaults.
  • Recording is never saved: a camera always starts with Record AVI off. Window layout, interface size, zoom and which Controls sections are open are not part of a profile.
  • A camera seen for the first time starts from the defaults in Defaults and limits (exposure 8000 µs, gain 0 dB, 30 fps, the default noise pipeline; the LabVIEW flow is off, also for the analog camera, which used to start in it). Exposure, gain and frame rate are still clamped to what the camera reports.
  • Reset camera to defaults… puts the displayed camera back to those defaults after you confirm, and clears its saved profile. Other cameras and your presets do not change.

Presets

A preset is a profile saved under a name you choose, which any camera can use. The Presets row sits in the Camera section:

  • Save as… asks for a name and saves the displayed camera's current settings. Names ignore letter case, so a name that is already used asks before it replaces that preset.
  • Pick a preset in the list, then Apply: it changes only the displayed camera, which keeps the new settings as its profile. A preset saved on another camera model still applies: the processing values in full, and exposure, gain and frame rate fitted into this camera's limits. The log lists every value that had to change and ends with Preset applied: <name> to <camera>.
  • Delete removes the chosen preset after you confirm; cameras keep their settings.
  • Hover a preset in the list to see the camera model it was saved from.

The built-in Live preview, Measurement and Peak hold buttons (top of ESPI measurement) are separate: they change only processing, never exposure, gain, frame rate or the LabVIEW flow, and they are not listed with your presets. To keep one together with your camera values, press it, then Save as….

Profiles and presets live in the program's own settings store (the registry on Windows, a preferences file on macOS and Linux), beside the window layout, not in output/.

Analog camera #

The Sony XC-ST50's composite video goes through a Hauppauge USB-Live2 into the PC, and the stick appears in the camera list as Hauppauge USB-Live2 (video N). Close WinTV and Hauppauge Capture first: the stick serves one program at a time.

  • Exposure, gain and frame rate are set by the camera's own switches, so those controls are disabled; the status line shows the measured capture rate.
  • Full interlaced frames by default, as the LabVIEW program used. Single field (interlaced camera) shows one of the two fields, doubled to full height, removing the 1/60 s offset between fields at the cost of half the vertical detail. Differences compare rows woven the same way, so the offset rarely matters for ESPI.
  • It starts in Reference view with Fixed gain 42× and the default noise pipeline: four frames averaged before the difference (which also averages the capture stick's own noise and line jitter), a 16-frame automatic reference and the Oriented speckle filter. Fixed gain, because Auto stretch would blow the capture noise (3–5 grey levels) up to full-contrast grain. The LabVIEW flow toggle gives the known-good LabVIEW ESPI 1.5 processing with that program's saved defaults instead (Fixed gain 42×, a one-frame automatic reference, no averaging or filters).
  • Raw difference on the toolbar shows the bare |live − previous| of the capture frames, with none of the above processing, to see what the camera itself delivers.
  • Images look about 12% wide because NTSC pixels are not square; they are not resampled. Expect coarser fringes than with the Blackfly.

A laptop's built-in camera (named for example Integrated Webcam, Integrated Camera or FaceTime HD Camera) is not listed at all: it is never an ESPI source.

Other video devices (webcams, other capture sticks) are listed as not yet supported and are never opened unless you choose one. When you switch one on, it runs as delivered, and the viewer files a GitHub issue labelled camera-support with what the device reports, once per device type. A copy without a feedback token saves the report to output/logs/camera-report-*.md and shows a Report this camera button instead.

Frequency generator and piezo (NI DAQ) #

Devices → Frequency generator and piezo (NI DAQ)… drives two signals from an NI multifunction DAQ such as the USB-6251: the frequency generator, which excites the specimen through its shaker or PZT amplifier, and the piezo driver, which sets the reference piezo through its amplifier. Frames are not synchronised to the generator's drive; the piezo's phase steps are, in the Phase view.

  • Device — the NI devices NI-DAQmx can see, plus a Simulated device (no hardware) for trying the controls; it drives nothing and is marked in red. Rescan looks again after plugging a device in.
  • Assign outputs — give each role its own output. The frequency generator can use an analog output (AO 0 or AO 1, a sine) or a counter (Counter 0 or Counter 1, a 0–5 V square wave on the PFI terminal you pick; on the USB-6251 BNC, PFI 0–7 have BNC sockets). The piezo driver uses an analog output. Choose Off to leave a role unassigned.
  • Frequency generator — Frequency, Amplitude (peak) and Offset. The line below says exactly what the device will produce: the sine is built from whole samples of a 20 MHz clock, so the frequency can be a few parts per million off what you typed.
  • Piezo driver — Hold a voltage (with Step − and Step + to move it by a set amount, for manual phase steps), or Sine at the generator's frequency with its own amplitude, centre voltage and Phase. The sine shares the generator's clock, so the phase between them is exact. Or Triangle at its own frequency: a ramp from Bottom up to Top and back, Frequency times a second (0.01–1000 Hz), starting at the bottom. This is the slow ramp a function generator used to feed the piezo amplifier; the line below says the frequency the device really produces. Both analog outputs share one sample clock, so a triangle needs the frequency generator off or on a counter.

    Follow the camera's frame rate sets the triangle's frequency for you, so the reference phase moves by Phase per frame (default 180°, half a wavelength of path) from one frame to the next: the frame rate is the rate frames really arrive from the displayed camera, and the frequency is set again whenever that rate moves it by more than 3% (each change restarts the triangle at its bottom). With Frames back N in the Previous view, use 180° / N. Piezo scale says where the piezo's phase per volt comes from: Calibrated uses the voltage per 90° that Calibrate phase step measured (run it once in the Phase view; it includes the mirror angle and the piezo), giving frequency = frame rate × volts per 90° ÷ (Top − Bottom). Manual works it out from Piezo travel (about 0.1 µm/V for a Thorlabs PE4), Amplifier gain (15 for the MDT694A at 150 V) and Mirror angle (the angle of incidence, 45° in the lab) for the HeNe laser (632.8 nm). Both are approximate (an open-loop piezo's travel varies with the span), so fine-tune Phase per frame by eye.

    Auto-tune (experimental) tunes the applied triangle's frequency from the camera frames instead, for a 180° step per frame, where the Previous-view difference is strongest and steadiest, and keeps it there. Apply a triangle with Piezo on first, use the Previous view and keep the object still. The piezo first holds still at the triangle's centre for a few seconds to measure the camera noise; then it compares frames one and two apart (at a 180° step, frames two apart match), finds which side of 180° the step is on with a small trial change, jumps close, and finishes with small steps. Each change restarts the triangle and is logged. It stops by itself when the displayed camera changes, the Phase view is chosen, new settings are applied or the outputs stop; if it cannot find the step it goes back to the computed frequency and says so. Turning it off keeps the tuned frequency.

  • Safety limit — each role refuses any setting that would go beyond this many volts. Set it to your amplifier's largest safe input before switching anything on. The piezo driver never goes below 0 V either: its amplifier, a Thorlabs MDT694A, takes 0–10 V on its EXT INPUT, and a negative input would drive the piezo below 0 V. For the MDT694A, set the piezo's limit to 10 V at most.
  • Apply sends the settings; All outputs to 0 V stops the generator and sets every assigned output to 0 V. An assigned output that is switched off is held at 0 V.
  • Safety checklist — the first Apply that switches an output on for a real device asks you to tick off a short checklist (the MDT694A's knob at zero, only the DAQ's cable on its EXT INPUT, its OUTPUT never to the DAQ, the limits suit the piezo, the generator's cable, someone watching). It lists only the checks for the outputs you are switching on. Nothing is driven until every box is ticked. Each output is allowed once per connection; switching on another one, or moving one to another socket, asks again. The simulated device never asks. The Phase view's piezo steps wait for it too.
  • Self-checks — every output is set to 0 V when the device connects. While connected, ESPI live reads its own outputs back about once a second through the USB-6251's internal channels (no extra cable); a reading that does not match what was written, or the window freezing for 2 s while an output is on, sets every output to 0 V and says why. Test outputs… steps each output to 0.5 V and back and checks it; switch the MDT694A off first.
  • Where to plug in… — a drawing of the USB-6251 BNC's front panel, laid out like NI's own figure of it, with the sockets your settings use marked and numbered, and beside it where each cable goes (the piezo driver's socket to the MDT694A's EXT INPUT, the generator's to the specimen drive). It follows the form while it is open. A counter on PFI 8–15 is marked on its row of the screw-terminal strip, since those have no BNC.

Wiring the piezo (Thorlabs MDT694A). Connect the DAQ's AO 1 BNC to the MDT694A's EXT INPUT (0–10 V) and leave its OUTPUT on the piezo. The MDT694A multiplies the input by 15 at its 150 V limit and adds the OUTPUT ADJ knob, so turn the knob to zero unless you want an offset on top, and keep Top × 15 + the knob at or below the limit lit on its front. Never connect the MDT694A's output (up to 150 V) to the DAQ.

All volts are at the DAQ, before your amplifiers. The DAQ cannot drive a shaker or piezo itself (±10 V, ±5 mA). Closing the window leaves the outputs running; they go to 0 V on an error and when ESPI live closes. Switch your amplifiers on after the DAQ is powered and ESPI live is running, and off before you unplug the DAQ: its outputs are undefined for a moment while it powers up.

NI support needs pylablib-lightweight and nidaqmx (the setup script installs them) and NI's NI-DAQmx driver from ni.com, on Windows or Linux. Without them only the simulated device is offered, and the window says what is missing. The log records every setting applied, including the frequency the device really produces.

Phase view (phase-shifting ESPI) #

Subtraction fringes are broken into speckle and lose the sign of the change. The Phase view instead steps the reference piezo through quarter-wave phase steps between frames, computes each pixel's speckle phase and shows its change since the phase reference, wrapped to one fringe: mid-grey is no change, black to white is 2π, and the direction of the ramp shows which way the surface moved.

  • Starting it — assign the piezo driver in the NI DAQ window and press Apply. From then on, whenever that device connects (at startup, or from the window) the displayed camera switches to the Phase view and its toolbar button appears. The piezo follows the displayed camera. Opening the DAQ window alone never drives the piezo.
  • Each step — the DAQ holds the piezo at the piezo Voltage plus N × Step, then the next Settle frames are dropped (they were exposed while the piezo moved; one more after the return to step 0), then Average N frames are averaged when Average camera frames is on. Every level stays inside the piezo's safety limit.
  • Phase steps — 5-step (Hariharan) (default) tolerates a step that is not exactly 90° and measures the step it made, shown in the status bar; 4-step is faster but turns a wrong step into ripple.
  • Phase filter (default 9 px) — smooths the phase change as its sine and cosine, weighting strongly interfering speckles, so it never blurs across the jump from white to black.
  • Reference — the first complete set after the view starts (or the piezo changes) is the phase reference; F takes a new one. Keep the object still while it is taken.
  • Calibrate phase step — with the object still, measures the step over five 5-step sets and sets the DAQ's step voltage for 90°; the voltage is saved with the DAQ settings.
  • Stopping — All outputs to 0 V, a DAQ error or a disconnect stops the stepping; the view then shows the camera frame and says what it needs.
  • Dummy mode — with the simulated device, the synthetic camera becomes a speckle interferometer that follows the simulated piezo (72° per 0.05 V, so calibration has something to correct) and a slowly growing dome.

Common operations #

Position, focus and inspect the image #

  1. Select Raw view.
  2. Use Exposure and Gain to get a well-exposed image.
  3. Use the toolbar Zoom slider, or the mouse wheel or trackpad on the image, to zoom up to 64×. At high zoom individual pixels are shown sharply.
  4. Drag with the left mouse button to pan while zoomed.
  5. Double-click the image to toggle between fit and 4× zoom. Press 0 for fit and 1 for 1:1.
  6. Watch the pixel readout in the status bar to check individual values.

Freeze and inspect an image #

  1. Press Space or click Freeze. The image holds and an amber FROZEN at bar appears; the camera, averaging, reference refresh and recording keep running.
  2. Zoom, pan and read pixel values on the held image.
  3. Press S to save the held image; the sidecar records when it was frozen. Set reference still captures the live camera frame.
  4. Press Space again to return to live. With several cameras, each keeps its own frozen frame; switching a camera off or to live drops it.

Read pixel values #

  1. Choose Reference (press F for a reference) or Previous.
  2. Click Pixels (P) or press P. A window opens with a square of the image enlarged, each camera pixel a cell with its value written on it. The square starts in the middle of the image and is outlined in yellow on the main image.
  3. Choose the Square size: 1 × 1, 2 × 2, 4 × 4 … up to 64 × 64 pixels (8 × 8 at first; the choice is remembered). Click the main image to move the square there.
  4. Read the values. In Previous and Reference view each is the raw absolute difference in camera levels (0–255), taken before the noise threshold, Difference gain, averaging and Scaling, so display settings do not change it: 0 means the pixel did not change, sensor noise gives a few levels at most, and movement or deformation raises it. With averaging before the difference on, they are the difference of the averaged frames. In Raw difference they are that view's |live − previous|; in Raw view they are the camera levels. Cells are shaded from black (0) to white (the largest value in the square), and the line above the grid gives the square's place and its min, mean and max.
  5. The values refresh ten times a second; click Freeze to hold them while you read. Large squares show numbers only when each cell is at least 16 screen pixels: enlarge the window.
  6. Without a reference the window says no reference yet (press F). The window follows the displayed camera; the outline is not part of saved frames or recordings.

Capture a reference and see a difference measurement #

  1. Put the specimen in its resting state.
  2. Select Reference view.
  3. For a noisy or analog camera, set Ref. frames to 8–30 first, and keep the specimen still while the frames are collected.
  4. Press F or click Set reference. The log confirms the capture, and the hint changes from asking for a reference to showing the difference view.
  5. To check the reference, press C: the comparison window shows it beside the current frame and the difference.
  6. Load, heat or otherwise deform the specimen. The image now shows absolute differences from the resting state.
  7. If the pattern is too faint, raise Difference gain or switch Scaling to Auto stretch.
  8. To start a new measurement from the current state, press F again.
  9. If the camera settings or illumination change, capture a new reference; otherwise the brightness change appears as a large false difference.

Measure frame-to-frame change instead #

  1. Select Previous view.
  2. The first frame becomes the baseline, then each displayed image is the difference from the frame before it. This is useful for spotting motion or vibration that is present right now.
  3. Press R (Reset last) after a disturbance to start a clean baseline.

Average and rolling average #

  1. Select Previous or Reference.
  2. Raise Average N. Start around 3–5 and increase until the fringes are stable; higher values mean a slower displayed update.
  3. Turn on Rolling average when you want a running average that still updates every frame, for watching fringes move.
  4. If a disturbance has just occurred and the image looks smeared, press A (Reset average) to restart the accumulation.
  5. For slow drift from air or heat, set Ref. refresh to a few seconds; 0 keeps one reference until you press F.
  6. Recording runs at the averaged rate unless Rolling average is on, so a large N produces a lower-frame-rate AVI with the same duration.

Reduce sensor noise #

  1. Raise Noise reduction in the Camera section to blend each frame with the previous ones (0–95%).
  2. Use the lowest value that cleans the background; high values leave a trail behind motion and weaken Previous-view fringes.
  3. Use Average N for difference-frame noise; these two controls solve different problems.

Get the best contrast #

  1. Pick Scaling: Auto stretch for a first look on the Blackfly; Fixed gain on the analog camera, raising Difference gain until the fringes are bright. The status bar shows the true input range.
  2. Use Speckle filter and Filter width to blur away pixel-scale speckle; keep the width well below the fringe spacing.
  3. Set Stretch clip to about 0.5% when a few stray speckles flatten the contrast; 0 is exact min/max.
  4. Adjust Gamma to brighten or darken the midtones, and Invert to swap bright and dark fringes.
  5. Use Fixed gain at 1× when you need to judge absolute difference values between frames; the status bar and pixel readout then show the unscaled values.

Save a still frame with notes #

  1. Type a Title, for example aluminium_plate_40C.
  2. Type any Notes: load level, temperature, specimen, lens, or anything needed to interpret the image later.
  3. Click Save frame or press S. If the display is frozen, the held image is saved and the sidecar records when it was frozen.
  4. The log shows the PNG path. If a title or notes were present, a matching .txt file holds them with the source (Camera or Demo).

The PNG contains exactly the current display, including gamma, stretch, invert and the demo watermark.

Record a measurement sequence #

  1. Set the view, averaging, gamma and contrast you want. These choices are baked into the recording.
  2. Click Record AVI. The status label beside the button shows the output frame rate.
  3. Perform the experiment. You can keep using the window while it records.
  4. Click Record AVI again to stop. The log prints the file path and a summary of frames written and skipped.
  5. Find the file under output/recordings/ (see Files and output folders).

Only the view mode, and Average N or Rolling average in Previous/Reference, start a new file. Changing gamma, Scaling, Difference gain, Stretch clip, Outlier filter, Speckle filter, Frames back, Invert, exposure, gain, FPS, noise reduction, Single field, Set reference, Reset last or Reset average continues the same file. Stop and restart the recording after any of those changes, or record them as separate files and note the change in your lab book.

Adjust exposure, gain and frame rate #

  1. Watch the Applied line under the camera controls.
  2. Increase Exposure for a brighter image and better signal-to-noise ratio, at the cost of motion blur and a lower maximum frame rate.
  3. Increase Gain only when exposure is already as long as the experiment allows.
  4. Set Requested FPS to the rate you need. If the resulting rate is lower, the camera, exposure or USB bandwidth is the limit.
  5. Raise Noise reduction only as needed; it cleans sensor noise in every view but trails motion and weakens Previous-view fringes at high values.
  6. For an interlaced analog camera, keep full frames (Single field off) unless line-to-line texture appears when the scene changes between fields.
  7. After changing camera settings, capture a new reference if you are measuring differences.

Arrange the workspace #

  • Drag the Controls or Log dock by its title bar to another edge or out of the window to float it.
  • Use View → Controls or View → Log to hide or show a panel.
  • Resize the window; the layout and size are restored the next time the app starts, shrunk to fit if the screen is now smaller.
  • On a short screen, scroll the Controls panel to reach the controls below the fold.
  • If the text and controls are too large or too small for your screen, change the Interface size slider in the Display section of the Controls panel: drag it and release, and the whole window (text, buttons, panels, status bar and dialogs) takes the new size at once, without restarting. It is remembered for the next run. Reset interface size to 100% returns to the standard size. View → Interface size offers Larger, Smaller and Reset, also on Ctrl++, Ctrl+− and Ctrl+0 (⌘ on a Mac). A size that would make the window larger than the screen is lowered until it fits. The image itself is not scaled: it still fills the room the panels leave.
  • On a small screen, hide the log while measuring and show it when you need to check a saved path or an error.

Switch from demo to live capture #

  1. Connect and power the camera.
  2. Make sure no other application (SpinView, another viewer, a script) is using it.
  3. Click Switch to live capture.
  4. If it succeeds, the red indicators disappear, the view resets to Raw, and any demo recording is stopped so synthetic and live frames never share a file. The switch also configures the camera at the current exposure, gain and FPS shown in the controls. Check the Applied readout before measuring. Capture a new reference before continuing.
  5. If it fails, a warning gives the reason and demo mode continues. Fix the connection and try again; no restart is needed.

Use several cameras #

  1. Connect the cameras. The Cameras section at the top of Controls then lists each one, with a Process row per camera.
  2. Pick the camera to show with Display. The controls, toolbar and shortcuts act on that camera.
  3. Leave Process checked on cameras that should keep acquiring, processing and recording in the background.
  4. Watch each row's rate and REC marker. If rates drop, lower the frame rate or move cameras to separate USB 3 controllers.
  5. Uncheck Process to stop a camera and release it; its settings are kept, but its reference and average start fresh when it runs again.
  6. Each camera keeps its own settings, also between runs. To give two cameras the same settings, save a preset on one (Save as…), display the other and press Apply.

Remote control #

While the app runs it serves a small control API on http://127.0.0.1:8364/, so a second terminal — or a script or AI agent — can query and drive the running instance. The server listens on the loopback interface only: nothing outside this computer can reach it, and there is no password, so do not forward the port to another machine.

The API describes itself: open http://127.0.0.1:8364/ (or curl it) for every endpoint, every setting with its type, choices and range, and every command. The built-in terminal client covers the same ground:

PYTHONPATH=src python -m espi_live control status                 # app and cameras at a glance
PYTHONPATH=src python -m espi_live control get                    # every setting of the shown camera
PYTHONPATH=src python -m espi_live control set exposure_us=5000 mode=Reference
PYTHONPATH=src python -m espi_live control set record=true --camera 12345678
PYTHONPATH=src python -m espi_live control run reference          # capture a reference frame
PYTHONPATH=src python -m espi_live control run save title=Band notes="before pump"
PYTHONPATH=src python -m espi_live control log --lines 100        # the run log's tail

set takes any setting name GET / lists; run takes save (with optional title and notes; a frozen display saves its held frame), reference, reset_previous, reset_average, switch_live, display, processing_on and processing_off. Use --camera to point at a camera other than the displayed one, by index, serial or label, and --json for raw output a script can read.

Changes apply through the running engines, and the window's controls follow along: a value set from the terminal shows up on the sliders within a moment and is saved to the camera's profile exactly like a hand-made change. Values are clamped the same way the controls clamp them — camera values to the device's own limits, the rest to the ranges the controls accept — and the reply's applied section shows what was actually used. A camera that is not processing must be started first: run processing_on --camera ….

The chosen port is written to output/control.json for the client to find; start the app with --control-port N to fix the port (useful with several instances: pass the same --port to the client) or --no-control to turn the server off. To script a windowless run instead, see the README's --headless --control section.

Files and output folders #

Everything is written under the project's output/ folder. In a packaged build, that folder sits next to the executable (next to the .app on macOS).

output/
  logs/        one log file per run
  frames/      saved PNG stills and their .txt sidecars
  recordings/  AVI recordings

File names use the camera's serial number (when several are used) and a local timestamp:

  • Frames: frame_<serial>_YYYYMMDD_HHMMSS_microseconds[_title].png
  • Recordings: espi_<view>_<serial>_YYYYMMDD_HHMMSS_microseconds.avi
  • Demo files add a dummy_ prefix.
  • Logs: output/logs/espi_<YYYYMMDD_HHMMSS_microseconds>.log.

Recordings are MJPG-compressed AVI files. They are capped at 30 fps and use the same gray values as the screen. A frame title or notes produce a sidecar text file with the frame name, source, title, notes and, for a frozen image, the time it was frozen.

Troubleshooting #

Click a symptom to expand it. The same information is in the log panel and the run's log file under output/logs/.

No camera was detected

The app offers demo mode. Check that the camera is powered, connected by a USB 3 port and cable, and not open in SpinView or another application. Then click Switch to live capture or restart the app. If PySpin is not installed, the log says so; on the camera PC run the setup script again.

Live capture switch fails

Read the warning dialog and the log. Common causes are another program holding the camera, a USB 2 port or hub, a loose cable, or a camera that has not finished booting. Demo mode keeps running so you can retry without losing the session.

The image is black in Previous or Reference view
  • Confirm a reference has been captured; the hint line says if one is missing.
  • With Scaling on Auto stretch, a constant difference image is all black by design. Disturb the specimen or use Fixed gain to inspect raw values.
  • Check that the view is not Raw after a live-capture switch.

A recording started before a reference exists, or before the first Previous baseline frame, contains black frames. Stop it, wait for a real difference image, then start the recording.

The image freezes and the status bar says “Waiting for camera frame”

The app has stopped receiving valid frames. Check the USB 3 cable and port, close SpinView or any other application using the camera, and restart the camera or the app. The log repeats Camera timeout or acquisition error every few seconds. The app does not reconnect automatically.

The displayed rate is lower than the camera rate

Read Processed and Displayed in the status bar. If Processed is low, the limit is acquisition: exposure, USB bandwidth, or the camera. Average N does not lower Processed; it lowers Displayed (see below).

If Processed is high but Displayed is low and Average N is 1, the window or graphics system is the bottleneck; hide the log or reduce the window size. The CPU fallback is selected automatically when OpenGL 3.3 is unavailable; it is not a performance option.

At full resolution the camera is rated 59 fps for Mono8 and the app caps the requested rate at 60 fps. At 8000 µs the exposure is not the limit; longer exposures can reduce the attainable rate. Use the resulting FPS readout as the authoritative value.

The log says “Display: CPU fallback”

The machine could not create an OpenGL 3.3 core context, common in some remote-desktop sessions. Everything still works, but the CPU draws and scales the image, so the display rate may be lower and large windows cost more CPU.

Recording skips frames or repeats frames

The AVI is written on a constant-rate timeline because encoders and players expect one. If the encoder cannot keep up, preview frames are skipped; if acquisition is slower than the output rate, the last frame is repeated. Lower Requested FPS or raise Average N to reduce the output rate. The log reports skipped frames and late intervals when the file is closed.

Recording stops by itself

Changing the view mode or Average N closes the current file and begins a new one. An encoder error also stops recording and turns the button off; the log contains the reason and any path that was saved.

A control snaps back or will not reach the value I typed

The camera is clamping the value, or the value is outside this build's fixed UI limits: exposure 0–50,000 µs, gain 0–30 dB and Requested FPS 0–60. The camera itself can reach 30 s and 47.99 dB, but those values are not exposed here. Check the Applied readout and the log.

Saved brightness does not match the screen

They should: saved frames and recordings are produced by the same gamma path as the display. Confirm you are looking at the file from the same run and that it is a demo file (watermarked) or a camera file as expected.

The application closes with an error

A fatal camera or processing error ends the run rather than leaving a broken measurement. A dialog shows the exception, and the full traceback is in the run's log file under output/logs/. Restart the app and, if it recurs, include that log when asking for help.

Updates, features and Codex #

There is one Qt front end; the old Tk interface is no longer part of the application.

Automatic updates

Packaged copies check GitHub at startup and offer a newer full release (pre-releases are skipped). A blue Update available button appears in the status bar and the log. Click it to download while measurement continues; the app verifies the SHA-256, then offers to restart. It finishes any recording, releases the camera, swaps in the new build and starts it with the same options. Choosing not to restart installs the update when you close the app.

  • Check for updates (the circular-arrow icon) in the status bar or Help → Check for updates… checks on demand; it is greyed out while a check runs. While the app stays open it also checks on its own every few hours.
  • The first start after an update shows a What's new window with the release notes of every release the update moved past, newest first, each with a link to its page on GitHub. It appears once and needs no network.
  • espi-live --update updates without opening a window; --no-update-check skips the startup check and source download.
  • The program's folder must be writable. Output, token files and recordings are never touched. A single-file build from build 6 or earlier cannot update itself to the folder layout; download a current release by hand once.
  • The build number is ordered by workflow run, so a copy never updates to an older build. Running from source does not self-update; use git pull.

Request a feature

Request feature (the light-bulb icon) in the status bar or Help → Request a feature… asks for a title, optional description and optional name, then files a GitHub issue labelled feature-request and enrich. The issue includes the build, platform and video source. Submit files it from the app; a blank description is written from the title, and text you write is kept and expanded. A copy without a feedback token says it cannot file the request.

Open in Codex

Packaged copies keep the source they were built from in espi-live-source/ next to the program. Open in Codex (the </> icon) in the status bar or Help → Ask Codex about the source code… opens OpenAI Codex on that folder, so you can ask how the program works. The button is greyed out (its tooltip reads Getting source…) while the source downloads first. A change approved in Codex is sent as a GitHub issue with --send-changes; it is not pushed with git from the app. Running from source opens the checkout itself.
